# SuperEGM 1.2.1 — design

Date: 2026-11-12. Status: brainstormed with the owner; awaiting `/superegm:review-spec`.

Rounds: 3

Inputs: the owner's 1.2.1 change list (eight items, 2026-11-12); the 1.2 integrate review
(`spec-2026-11-03-superegm-design-integrate-c1`, 0 high, 7 medium, 8 low, deferred to 1.2.1 by the
owner on 2026-11-10); the 1.2 build's launch record (84 launches, median 19 minutes, the large units
of the 1.0 build relaunched up to 11 times); the 1.2 design,
[docs/specs/2026-11-03-superegm-design.md](2026-11-03-superegm-design.md), which this design amends
and does not restate.

## 1. Intent

1.2 made SuperEGM runnable while the owner is away. Running it for real showed four places where
the owner still does work a machine could do, or where the fixed rules fit one project badly:

- **Every phase waits for a typed command**, even the ones that are mechanical once the spec is
  settled: plan, plan review, file, wave. The owner's judgement is spent on the spec; after
  approval it should be spent only on the decisions the workflow raises.
- **Five review rounds is too many for most work**, and the number is a constant.
- **Severity alone decides what blocks.** A medium that only a hand-forged in-process object can
  trigger, and that is easy to fix later, blocks a merge as hard as one an HTTP caller can trigger.
  Each project wants its own rule, and the rule must be written down before the build, not argued
  per finding.
- **Units are too big.** The 1.0 build's units of 59–94 KB, 22–52 files and 26–60 steps took up
  to 11 launches each; a 24 KB, 8-file, 16-step unit merged first time. The 49 KB body limit lets
  the big ones through.

And one place where the owner pastes the same text by hand: repository rules that every builder,
reviewer and judge should see (a Relay registration step, a house standard) go into every issue
body today.

1.2.1 fixes those, and pays down the integrate review's deferred findings.

## 2. Goals, non-goals, anti-goals

Goals:

1. From the spec's approval commit to the first builder launch, nothing waits for a typed command
   (section 7).
2. The review round cap is configuration, default 3, and a spec may set its own (section 4).
3. A spec may declare triage fields and the patterns under which a medium stops blocking; the
   foreman triages every high and medium on a pull-request head against them (section 5).
4. One configuration list routes repository instruction files to builders, the foreman, reviewers
   and judges, recorded as an exposure (section 3).
5. Unit size limits are configuration with the 1.0 build's evidence as the default; the plan splits,
   and `scan` refuses (section 6).
6. The deferred integrate findings are fixed or written into this design (section 8).

Non-goals:

- Merging. The driver never merges, in either mode; nothing in this design changes who merges.
- Triage on spec and plan reviews. Those reviews are unchanged.
- A per-finding override of the triage rules. A rule change is a spec change and needs a new
  approval.
- Remote builder hosts (the AgentCore line of work). The launch contract is unchanged.

Anti-goals:

1. **A high never stops blocking by triage.** No pattern may name `high`; `approve-spec` refuses one.
2. **No instruction reaches an agent unrecorded.** A dispatch that carried an instruction file
   records it, the way `exposed:orient <tree sha>` records the orient file today; a review or judge
   round whose brief carried one is never recorded `clean`.
3. **Relay or chat text is never an instruction channel.** An instruction file is a committed file
   at a known commit; rulings still come only from the `**Ruling:**` grammar from `config.owners`.

## 3. Repository instructions (items 0 and 4)

### 3.1 The key

```json
"instructions": [
  {"file": ".superegm/rules.md", "to": ["builder", "foreman", "reviewers", "judges"]},
  {"file": ".superegm/relay.md", "to": ["builder"]}
]
```

- `file`: a path relative to the repository root. `to`: a non-empty list from `builder`,
  `foreman`, `reviewers`, `judges`. Default `[]`.
- Each brief for a role carries one `# Repository instructions` heading, then each file addressed to
  that role, in list order, under a `## <file>` line, verbatim.
- **Where it is read.** A builder, the foreman, and head reviewers read the file at the unit's base
  commit, as `pr_block_file` is read today. Spec and plan reviewers and the judges read it at the
  commit the review opened on. The Astra lane is a reviewer: a file addressed to `reviewers` leaves
  the machine to the Codex vendor; `docs/privacy.md` says so.
- **Recorded.** Every dispatch whose brief carried a file records `exposed:instructions <file>
  <12-hex blob sha>` in its isolation, one entry per file, joined with `; ` to any other exposure.
  The builder's launch entry gains `instructions: [{file, sha}]`.
- **Refusals.** A listed file absent at the commit it is read from refuses the launch or the
  dispatch, naming the file and commit; `doctor` prints the same line before the first wave.
- **Tools stay where they are.** A file cannot grant a tool. A builder file that tells the builder to
  run a command still needs that command in `builder.allowed_tools`; `doctor` warns (best effort: a
  line starting with a backticked command whose first word no `Bash(<prefix>:*)` entry allows).
- `pr_block_file` is unchanged: it is text for the pull request body, not an instruction.

### 3.2 The relay example

The owner's Relay registration is the first user. `.superegm/relay.md` addressed to `builder` says
to run, once at start, `printf '{}' | <probe> relay socket-request --socket '<sock>' --method POST
--path /register`, and `builder.allowed_tools` gains `Bash(printf:*)` and the probe's `relay`
prefix. Subagents (reviewers, judges, the foreman) cannot register (the relay identifies a session
by its process) and are never addressed with it.

## 4. The review round cap (item 1)

- `review.rounds`: an integer 1–10, default **3**. It replaces the constant `CAP = 5`
  (`skills/plan/scripts/superegm/review.py:52`) for spec, plan and head reviews.
- A spec may carry one `Rounds: <n>` line before its first H2 (this document carries `Rounds: 3`).
  `approve-spec` parses it and freezes it in the approval record; it then governs that handoff's plan
  and head reviews. It cannot govern the spec's own review, which runs before approval.
- The rest of the cap is unchanged: one more round per `continue` ruling; at the cap the owner (or
  in leavemealone the panel) rules continue, accept, or stop; an early accept (`acceptable:`,
  `decision open --point 5`) works below any cap.
- A cycle opened under 1.2.0 keeps the cap it opened with: the review record stores `cap` at open,
  and a record without one reads as 5.

## 5. Triage (items 2 and 3)

### 5.1 In the spec

Triage is declared by a spec's optional `## Triage` section. No section: triage is off, and the
1.2 rule (a high or medium blocks until fixed or ruled) stands. The grammar, three lists:

```markdown
## Triage

Fields:
- reach: external | agent | config | forged
- later: easy | migration | version
- critical: yes | no

Required:
- high: reach, critical, verified
- medium: reach, later, verified

Unblock:
- reach: forged, later: easy
- critical: no, later: easy, verified: confirmed
```

- `Fields`: a field name and its values. `verified` is built in and may not be declared: its value
  is `confirmed <file:line>` or `refuted <reason>`, and it matches a pattern as `confirmed` or
  `refuted`.
- `Required`: the fields each severity's triage must answer. `high` and `medium` only; a severity
  with no line requires `verified` alone.
- `Unblock`: patterns, each a set of `field: value` pairs, all of which must hold. A pattern applies
  to mediums only.
- The example's fields are the owner's starting set: **reach** (can an HTTP caller, an agent
  action, or a plausible configuration mistake trigger it, or only a hand-forged in-process object?),
  **later** (easy to fix later, or does the fix need a migration or a new declaration version?),
  **critical** (on the critical path with serious ramifications?).

The brainstorming skill offers the section and writes it with the owner. Spec review checks it:
`structural` for the grammar, the content lanes for whether the patterns are safe for the project.
`approve-spec` parses it, refuses a malformed section with the line at fault (and any pattern that
names a severity, anti-goal 1), and freezes the parsed rules into the approval record. The wave
reads the frozen copy only; editing the section needs a new approval.

### 5.2 On a pull-request head

- After a head review round is recorded, the foreman triages every high and medium of that round:

  ```
  superegm review triage --review <id> --finding <fid> --reach external --later easy \
    --verified "confirmed skills/x.py:41"
  ```

  One flag per declared field, plus `--verified`. The helper refuses: triage off; an unknown field
  or value; a missing required field; a `confirmed` without `<file:line>` that exists at the head; a
  finding not high or medium; a second triage of the same finding in the same round.
- The foreman verifies against the code at the head, in the worktree it already reads; `verified`
  states what it checked.
- A **medium** whose triage matches any `Unblock` pattern no longer blocks: it gets the disposition
  `deferred: triage <pattern n>`, one journal line, one row in the unit's follow-up list
  (`foreman/<unit>.json.followups[]`), and the head review's comment shows it under **Deferred by
  triage**. The builder may still fix it.
- A **high** always blocks, whatever its triage says. Its triage is still recorded, and shown to the
  owner or panel when the high is escalated.
- An untriaged high or medium blocks, as in 1.2. A clean outcome needs every high and medium fixed,
  ruled, or deferred by triage.
- `close` lists every handoff's follow-ups in its closing note, and `integrate` hands them to the
  integrate reviewers.

## 6. Unit size (item 5)

```json
"units": {"max_body_kb": 25, "max_files": 10, "max_steps": 15, "max_unit_deps": 2,
          "target_changed_lines": 600}
```

- **Limits** (`max_*`): a unit's rendered body at most 25 KB (it replaces `BODY_LIMIT = 49_152`,
  `__init__.py:65`), at most 10 `Scope paths`, at most 15 steps, at most 2 units in `Blocked by`.
  The release's closing sweep is exempt from `max_unit_deps`, as it is from the cross-subsystem rule.
- **Target** (`target_changed_lines`): the plan aims each unit at one behaviour reviewable as one
  pull request of about 600 changed lines. Nothing refuses on it.
- **The plan splits.** The plan skill checks each unit against the limits before writing it, and a
  unit over any limit is written as two or more, each with its own row through
  `approve-spec --amend-units`. `scan` refuses a plan with any unit over a limit, naming the unit,
  the limit and the value; its `warnings[]` keep their split-candidate role below the limits.
- **Evidence.** The 1.0 build's U01 (24 KB, 8 files, 16 steps) merged first time; U09 (94 KB, 25
  files, 44 steps) took 11 launches; U02–U07 (59–94 KB, 22–52 files, 26–60 steps) went the same way.
  Under these limits U09 would be three or four units and U02–U07 two or three each.

## 7. The chain (item 6)

### 7.1 What runs

Once a spec's approval commit is in the store, the driver advances the handoff one phase per tick,
the same phases the owner types today:

| The store shows | The tick runs |
|---|---|
| an approval, no plan | `/superegm:plan <spec>` |
| a plan, its review not converged | `/superegm:review-plan <spec>` |
| a converged plan review, no issues | `/superegm:file <spec>` |
| filed issues, units not all landed | `/superegm:wave <spec> --handoff <id>` |
| every unit landed | nothing; the inbox says `ready to integrate` |

- The store's state is the only input: the driver computes the phase with one helper,
  `superegm next --handoff <id>`, which prints the phase word (`plan`, `review-plan`, `file`, `wave`,
  `integrate`, `waiting <decision>`) and is the table above in code.
- `approve-spec` registers the store when it is not registered yet (`superegm register`), so the
  driver sees the handoff without a typed step.
- `driver.chain` (default `true`) turns this on; `false` keeps 1.2's behaviour, the driver running
  only `wave` in leavemealone.
- Integrate stays typed: it closes the handoff, and the owner reads its result.

### 7.2 Normal mode and leavemealone

- **Normal mode** stops only where a phase needs the owner: a decision point (a plan review at its
  cap, an escalated finding, a unit's stop question). The phase opens the decision as today and
  exits; the inbox and the notify hook carry it; the owner answers in the inbox or with a
  `**Ruling:**` comment; the next tick sees the ruling and resumes. `next` prints `waiting <id>`
  while a decision is open, and the tick runs nothing.
- **Leavemealone** never stops: the judge panel rules each decision, as it does in the wave today.
- The run cards, journal lines and records are the same in both modes; only who answers a decision
  differs.
- Merging stays the owner's. The wave's clean heads wait for the owner's merge as in 1.2.

## 8. The deferred integrate findings

The owner deferred the 1.2 integrate review's findings to 1.2.1 on 2026-11-10. This design settles
each:

- **design-1-2, zoom-out-1-1 (medium): self-registration.** Finish U32's design: each module's
  `CONFIG_DEFAULTS`, `INIT_STEP` and `DOCTOR_CHECKS` are the only source; `doctor.py`'s central
  lines and `load_config`'s duplicated defaults (`stall_minutes`, `max_subagent_calls`) go; a module
  with nothing to register declares nothing (the ~30 empty copies go, `discover()` reads absence as
  empty). The 1.2.1 keys (`instructions`, `review.rounds`, `units`, `driver.chain`) register this
  way from the start.
- **zoom-out-1-2, zoom-out-1-3 (medium, low): two ingest paths.** The spec-PR and head ingest
  paths share one writer, with ids numbered per round and the resumable plan file; `ingested[]` is
  derived from the findings' `thread` field and no longer stored.
- **design-1-3, zoom-out-1-4 (medium): the early accept's lapse.** The landed rule is adopted as
  designed, stated here: an accept given below the cap holds its round alone. It lapses once a later
  round completes, once a later round holds an unsettled high or medium, or once a finding recorded
  into its round since (an ingested external one, a set finding) bars it; the cap's accept stands.
  Once a verdict replaced the accept's `converged: by ruling <id>` mark, the accept never returns.
  No code change.
- **zoom-out-1-5 (medium): `STORE`/`CURRENT_ARGS`.** The module globals go; `atomic_write`'s write
  guard and the driver's per-store tick take the store as a parameter (`driver.tick_store` no longer
  assigns `core.STORE`).
- **design-1-1 (medium): an interrupted launch.** `interrupt` and a killed launch read
  `subagent_calls` from the session id on the launch entry, as the 1.2 design says.
- **design-1-4 (low): the judges' order.** The landed default order fable, opus, astra is adopted;
  the 1.2 design's order is superseded. No code change.
- **design-1-5 (low): the Scope-paths warning.** Superseded by `units.max_files` (section 6).
- **zoom-out-1-6, 1-7 (low): rulings.** One renderer for the `**Ruling:**` text; ingest decides
  "is a ruling" with `ruling_of`, not a string prefix.
- **zoom-out-1-8, 1-9 (low): duplicates.** Inbox's process kill is renamed for what it does
  (SIGKILL on a process); `driver.close_card` calls runcard's closer.
- **zoom-out-1-10 (low): test helpers.** `traces.py`'s `trace_directory` and `assert_child_probe`
  move to the tests.

## 12. Alternatives Considered

team: off (subagents not run; the owner brainstormed in conversation)

- **One key per audience** (`builder.orders_file`, `context_file`, …) for instructions. Rejected:
  every new audience would add a key and a code path; one list with `to` covers them all.
- **Triage rules in `config.json`.** Rejected by the owner: the rules decide what may merge with a
  known defect, so they belong in the reviewed, approved spec, frozen at approval.
- **Triage that may unblock a high.** Rejected by the owner (anti-goal 1).
- **Keep the cap fixed at 5.** Rejected: the 1.2 build showed most heads settle by round 3, and the
  right number is per project.
- **Chain only in leavemealone.** Rejected by the owner: the phases after approval are mechanical in
  either mode; normal mode differs only in who answers a decision.
- **Paste the Relay lines into each issue.** Rejected: it is per-issue toil and unrecorded.
- **A changed-lines limit that refuses.** Rejected: the line count is known only after the build;
  it stays a planning target.

Owner's answers in the brainstorm: cap default 3, a spec's `Rounds:` line overriding it for its
plan and head reviews; triage rules in the spec, highs never eligible; instructions for all four
audiences; the chain in both modes; the size limits as in section 6; SuperEGM's own builders as in
section 9.
