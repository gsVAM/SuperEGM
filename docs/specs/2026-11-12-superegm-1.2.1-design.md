# SuperEGM 1.2.1 — design

Date: 2026-11-12. Status: brainstormed with the owner; in `/superegm:review-spec`.

Inputs: the owner's 1.2.1 change list (2026-11-12, given in conversation; this design is its record);
the 1.2 integrate review (`spec-2026-11-03-superegm-design-integrate-c1`, 0 high, 7 medium, 8 low,
deferred to 1.2.1 by the owner on 2026-11-10; section 8 restates each finding it settles); the 1.0
build's unit sizes and launch counts (section 6); the 1.2 design,
[docs/specs/2026-11-03-superegm-design.md](2026-11-03-superegm-design.md), which this design amends
and does not restate. Where this design contradicts a passage of the 1.2 design, the passage is named
in section 2.1 and this design wins.

Owner's answers in the brainstorm: cap default 3, a spec's `Rounds:` line overriding it for its own
handoff; triage rules in the spec, highs never eligible; instructions for builders, the foreman,
reviewers and judges; the chain in both modes; the size limits of section 6; SuperEGM's own builders
as in section 10.

## 1. Intent

1.2 made SuperEGM runnable while the owner is away. Running it for real showed four places where
the owner still does work a machine could do, or where the fixed rules fit one project badly:

- **Every phase waits for a typed command**, even the ones that are mechanical once the spec is
  settled: plan, plan review, file, wave. The owner's judgement is spent on the spec; after
  approval it should be spent only on the decisions the workflow raises.
- **Five review rounds is too many for most work**, and the number is a constant.
- **Severity alone decides what blocks.** A medium that only a hand-forged in-process object can
  trigger, and that is easy to fix later, blocks a merge as hard as one an HTTP caller can trigger.
  Each project wants its own rule, and the rule must be written down before the build, not argued
  per finding.
- **Units are too big.** The 1.0 build's units of 59–94 KB, 22–52 files and 26–60 steps took up
  to 11 launches each; a 24 KB, 8-file, 16-step unit merged first time. The 48 KiB body limit lets
  the big ones through.

And one place where the owner pastes the same text by hand: repository rules that every builder,
reviewer and judge should see (a house standard, a registration step) go into every issue body today.

1.2.1 fixes those, and settles the integrate review's deferred findings.

## 2. Goals, non-goals, anti-goals

Goals:

1. In a store the owner registered, from the approval commit at `origin/<base>` to the first
   builder launch, nothing waits for a typed command except a decision the workflow raises
   (section 7).
2. The review round cap is configuration, default 3, and a spec may set its own (section 4).
3. A spec may declare the patterns under which a medium stops blocking; on every pull-request head
   a triage goldfish answers fixed triage fields for each medium, and a match defers it (section 5).
4. One configuration list routes repository instruction files to builders, the foreman, reviewers
   and judges, frozen at approval and recorded on every dispatch (section 3).
5. Unit size limits are configuration with defaults taken from the 1.0 build; the plan splits, and
   `scan` refuses (section 6).
6. Each deferred integrate finding is fixed or settled in this design (section 8).

Non-goals:

- Merging. The driver never merges, in either mode; nothing in this design changes who merges.
- Triage on spec, plan and integrate reviews, and on highs. Those are unchanged.
- A per-finding override of the triage rules. A rule change is a spec change and needs a new
  approval.
- Registering a store without the owner. `superegm register` stays the owner's typed opt-in.
- Remote builder hosts (the AgentCore line of work). The launch contract is unchanged.

Anti-goals:

1. **A high never stops blocking by triage.** Triage covers mediums only; a high is never triaged
   or deferred.
2. **No instruction reaches an agent unrecorded.** Every dispatch whose brief or prompt carried an
   instruction file records the file and its blob sha in its own `instructions[]` field (section
   3.1). The isolation field still comes from the agent's `saw:` line alone, so a hook's exposure
   stays visible on its own.
3. **SuperEGM reads no instruction or ruling from chat or Relay.** An instruction file is a
   committed file at the approval commit; rulings come only from the `**Ruling:**` grammar from
   `config.owners`, or from the owner in an interactive session.

### 2.1 Passages of the 1.2 design this design supersedes

- Section 2's non-goal "Chaining phases" and the glossary's **driver** "chains nothing": the driver
  chains plan, review-plan, file and wave (section 7). It still never types `integrate`.
- The "one human step" paragraph after the phase table ("the owner then types the next phase;
  nothing chains"): the push stays the owner's; the next phase is the driver's.
- Section 3's anti-goal 3, the closed list of what a builder sees: it gains the instruction files
  addressed to `builder` (section 3).
- Section 3's goal "every Claude goldfish and judge is isolated by construction": it still holds for
  the adapter; a goldfish or judge now also reads the instruction files addressed to it, recorded per
  dispatch (anti-goal 2).

## 3. Repository instructions

### 3.1 The key

```json
"instructions": [
  {"file": ".superegm/rules.md", "to": ["builder", "foreman", "reviewers", "judges"]}
]
```

- `instructions` (default `[]`) is a list of entries. `file`: a path relative to the repository
  root. `to`: a non-empty list from `builder`, `foreman`, `reviewers`, `judges`. Registered by the
  new module `skills/plan/scripts/superegm/instructions.py`.
- **Frozen at approval.** `approve-spec` copies the list into the approval entry with each file's
  12-hex blob sha at the approval commit, and refuses an entry whose file is absent there. A later
  config edit governs the next approval only, so an in-flight handoff never meets a file its base
  lacks.
- **Where it is read.** Every role of a handoff reads each file at the approval commit, by the frozen
  sha: a builder, the foreman, head reviewers, plan reviewers, integrate reviewers and every judge
  panel. Nothing a builder commits on its branch or pull request reaches any brief. A spec reviewer,
  before any approval, reads the file at the commit `HEAD` names when the round's brief is written.
- **One renderer.** `superegm instructions --role <role> [--handoff <id>] [--spec <path>]` prints the
  section and is the only source of it: one `# Repository instructions` heading, then each file
  addressed to that role, in list order, under a `## <file>` line, its text verbatim inside a fenced
  block (so its own headings never read as the brief's), placed last in the brief or prompt. With
  `--json` it prints `[{file, sha}]`. `launch-builder` calls the same function; the elephant and the
  foreman paste its output into the briefs they write.
- **Recorded.** The builder's launch entry, each review round's reviewer record (`review record
  --instructions <json>`), the judge panel's member record and the foreman's dispatch entry in
  `foreman/<unit>.json` gain `instructions: [{file, sha}]`; an empty list when none was addressed.
- **Tools stay where they are.** A file cannot grant a tool: a command it asks the builder to run
  still needs a `builder.allowed_tools` entry the owner adds.
- `pr_block_file` is unchanged: it is text for the pull request body, read at the launch's ref, not
  an instruction.
- The Astra lane is a reviewer: a file addressed to `reviewers` goes to the Codex vendor with the
  brief; `docs/privacy.md` says so.

### 3.2 First user

The owner's first file is addressed to `builder` only: a one-time registration command at the start
of each builder session (Relay, the owner's agent-messaging service). It is the owner's file, not
part of this design; the owner adds the command's prefix to `builder.allowed_tools`. Subagents
(reviewers, judges, the foreman) are never addressed with it: a registration names a session's
process. The risk of what such a channel then delivers is section 9's.

## 4. The review round cap

- `review.rounds`: an integer 1–10, default **3**, registered by `review.py`. It replaces the
  constant `CAP = 5` (`skills/plan/scripts/superegm/review.py:52`) for every review kind: spec, plan,
  head and integrate. The judge panel's own `CAP = 5` (`skills/plan/scripts/superegm/judges.py:25`)
  is unchanged.
- A spec may carry one `Rounds: <n>` line, `n` 1–10, before its first H2. `approve-spec` parses it,
  refuses any other value with the line, and freezes it in the approval entry; it governs that
  handoff's plan, head and integrate reviews. It cannot govern the spec's own review, which runs
  before approval under `review.rounds`.
- A cycle stores `cap` when it opens and keeps it; a record without one (opened under 1.2.0) reads
  as 5.
- The rest is unchanged, kind by kind: one more round per `continue` ruling; at the cap a spec, plan
  or integrate review is ruled continue, accept or stop, a head continue, stop or redesign (its
  accept stays refused, `review.py:1650`); an early accept below the cap works as in 1.2.

## 5. Triage

### 5.1 In the spec

Triage is declared by a spec's optional triage section: the first H2, outside a fenced block, whose
text after an optional `<n>. ` is `Triage`. No section: triage is off, and the 1.2 rule (a high or
medium blocks until fixed or ruled) stands. Inside the section the parser reads one `Unblock:` line
and the `- ` lines after it; any other line is prose and ignored.

```markdown
## Triage

Unblock:
- reach: forged, later: easy
- critical: no, later: easy, verified: confirmed
```

- The fields are fixed, and every triage answers all four:
  - **reach** `external | agent | config | forged`: can an HTTP caller, an agent action, or a
    plausible configuration mistake trigger it, or only a hand-forged in-process object?
  - **later** `easy | migration | version`: easy to fix later, or does the fix need a migration or a
    new declaration version?
  - **critical** `yes | no`: on the critical path with serious ramifications?
  - **verified** `confirmed <file:line> | refuted <reason>`, matched as `confirmed` or `refuted`.
- `Unblock`: patterns, numbered 1, 2, … in order, each a set of `field: value` pairs that must all
  hold. A pattern applies to mediums only.
- `approve-spec` parses the section, refuses an unknown field or value with the line at fault, and
  freezes the patterns into the approval entry. The wave reads the frozen copy only; editing the
  section needs a new approval.
- The brainstorming skill offers the section and writes it with the owner. Spec review checks it:
  `structural` the grammar, the content lanes whether the patterns are safe for the project.

### 5.2 On a pull-request head

- **Who triages.** After a head round is recorded and before `review post`, the foreman dispatches
  one `triage` goldfish (a new zero-context, read-only adapter, `superegm:triage`) with the frozen
  patterns' field list and every eligible medium of the round. It reads the code at the head in the
  review worktree and writes one line per finding:
  `<fid> | reach: <v> | later: <v> | critical: <v> | verified: confirmed <file:line> | refuted <reason>`.
  The foreman records the file verbatim with `superegm review triage --review <id> --round <n>
  --file <path> --isolation <…> --runcard <card>`; it neither writes nor edits a value. The foreman,
  which drives its unit to land, is not the triager.
- **Eligible.** A panel medium of the round that is not a regression, not a `test-delta:` finding,
  not named in an `owner:` line, and not an `external:<login>` finding. Every other finding blocks
  as in 1.2.
- **Refusals.** Triage off; a finding not eligible; an unknown value; a missing field; a `confirmed`
  whose `<file:line>` does not exist at the round's head; a second triage of a finding.
- **Deferred.** An eligible medium whose triage matches any pattern no longer blocks: it gets the
  disposition `deferred: triage <n>`, one journal line, one row in `foreman/<unit>.json.followups[]`
  (`fid`, claim, triage, pattern), and the review comment `render_comment` builds lists it under
  **Deferred by triage**. The builder may still fix it.
- **Undo.** The owner's `**Ruling:** <fid> finding upheld (fix it)` on a deferred medium restores
  blocking, as a point 1 ruling does today.
- A medium triaged `refuted` matches a pattern only if the pattern names `verified: refuted`; no
  example does. A non-matching medium blocks as in 1.2.
- A clean outcome needs every high and medium fixed, ruled, or deferred by triage.
- `close` lists the handoff's follow-ups in its closing note, and `integrate` passes them to the
  integrate reviewers.

## 6. Unit size

```json
"units": {"max_body_kb": 25, "max_files": 10, "max_steps": 16, "target_changed_lines": 600}
```

- **Limits.** A unit's rendered body at most `max_body_kb` × 1024 bytes (25,600), at most
  `max_files` `Scope paths`, at most `max_steps` steps. Registered by `scan.py`. The body limit
  applies to unit bodies only; `BODY_LIMIT = 49_152` (`skills/plan/scripts/superegm/__init__.py:65`)
  stays the limit of titles, the tracking issue and comments (`scan_text`). Size `L`'s scope-path
  limit becomes `max_files`; `S` (3) and `M` (8) are unchanged.
- **Target.** The plan aims each unit at one behaviour reviewable as one pull request of about
  `target_changed_lines` changed lines. Nothing refuses on it.
- **The plan splits.** The plan skill checks each unit against the limits before writing it. A unit
  over a limit is written as two or more; when the split needs a row the spec's `## Units` table
  lacks, the plan stops for `approve-spec --amend-units`, which the owner types, as in 1.2 (section
  7.2). `scan` refuses a plan with any unit over a limit, naming the unit, the limit and the value.
  `scan`'s 24,576-byte warning goes (the limit replaces it); its 10-step warning stays.
- **Evidence.** The 1.0 build's U01 (24 KB, 8 files, 16 steps) merged first time; U09 (94 KB, 25
  files, 44 steps) took 11 launches; U02–U07 (59–94 KB, 22–52 files, 26–60 steps) went the same way.
  The defaults are U01's size, rounded up. Under them U09 would be three or four units.
- **Frozen fields carried.** An `--amend-units` entry copies the frozen `rounds`, `triage`, `mode`
  and `instructions` of the entry it extends; every reader takes them from the handoff's latest
  approval entry.

## 7. The chain

### 7.1 What runs

The chain runs only in a store the owner registered with `superegm register` (unchanged), only when
`driver.chain` is `true` (the default; registered by `driver.py`), and only once the driver is
installed. `false` keeps 1.2's driver exactly.

**The mode is frozen.** `approve-spec` records `mode` (`leavemealone` with `--leavemealone` or
`config.mode` so, else `normal`) in the approval entry. The tick passes `--leavemealone` to every
phase it types iff that mode is `leavemealone`.

**The phase.** One helper, `superegm next --handoff <id>` (new `next.py`), reads the store and prints
one word, first match wins:

| The store shows | `next` prints | The tick runs |
|---|---|---|
| the handoff closed, or its latest approval voided | `none` | nothing |
| a `chain/<handoff>.json` wait record | `waiting <phase>: <question>` | nothing |
| the spec at `origin/<base>` is not the approved bytes or a later link (`launch.origin_problems`) | `waiting push` | nothing |
| no plan | `plan` | `/superegm:plan <spec>` |
| a plan review stopped, or stalled (`review status` exit 5) | `waiting review-plan: <review id> <stopped\|stalled>` | nothing |
| a plan review not converged | `review-plan` | `/superegm:review-plan <spec>` |
| no complete verification receipt matching the confirmed plan (`receipt_ok`) | `file` | `/superegm:file <spec>` |
| a unit neither landed nor stopped | `wave` | `/superegm:wave <spec> --handoff <id>`, gated by `status.tick_trigger` as in 1.2 |
| every unit landed or stopped | `integrate` | nothing; the inbox says `ready to integrate` |

Each run gets `--leavemealone` per the frozen mode. `wave` keeps 1.2's nothing-to-do predicate, so a
wave whose heads wait for the owner's merge starts no session; an owner's `**Ruling:**` comment is a
`tick_trigger` event (`status.ruling_facts`), so a wave session starts to apply it.

**The launch, by phase.** Everything 1.2 does for a tick's `wave` it does for the phase it typed:

- the launch entry in `driver/<handoff>.json` gains `phase`;
- `runcard open` gives the driven top-level card of that phase `driver_card` and `boot_id` and
  exempts it from the live-tick refusal, as it does a driven `wave` card today
  (`skills/plan/scripts/superegm/__init__.py:487-498`);
- the success, failure, exit-file and reboot proofs (`counted_failures`, `exit_file_proof`,
  `tick_trigger`'s `reboot`/`exit-file`) read top-level cards of the launch's phase; a launch of a
  phase other than `wave` succeeded when its card closed and its exit code is 0;
- `tick_store` asks `next` first and skips a handoff only on `none`, `waiting …` or `integrate`.

Integrate stays typed: it closes the handoff, and the owner reads its result.

### 7.2 Decisions under the chain

- **Before filing (plan, review-plan, file).** A headless phase cannot ask. Where it would ask the
  owner in normal mode (the plan's decision point 3, review-plan's start question and its
  per-round accept question, a contested high or medium, a review at its cap, file's
  Create / Change the plan / Stop) or must stop in either mode (a split needing `--amend-units`), it
  writes `superegm next wait --phase <phase> --question <text> --runcard <card>` and exits. The
  record is `chain/<handoff>.json` (`phase`, `question`, `since`). Under the driver, review-plan's
  start question is skipped (the chain already chose to start). The owner answers by typing the
  phase's skill in an interactive session, which asks the question, records the answer as today and
  clears the record with `superegm next clear`. The inbox and the notify hook carry the question.
- **After filing (wave).** Normal mode: the headless wave opens points 1, 2, 3 and 5 as `decision
  open` records (as the leavemealone wave does) instead of asking, and exits; the owner answers in
  the inbox or with a `**Ruling:**` comment, which the next tick's `tick_trigger` sees.
- **Leavemealone** routes to the judges only what 1.2 routes to them: before filing, the panel rules
  as the plan and review-plan skills do today, and file creates; after filing, the wave as today.
  Owner-only outcomes (a `test-delta:` finding, an `owner:` line, a split needing `--amend-units`)
  and every question a panel leaves unconverged become a wait record or an open decision, never a
  new panel on the next tick.
- The run cards, journal lines and records are the same in both modes; only who answers differs.
- Merging stays the owner's. Clean heads wait for the owner's merge as in 1.2.

## 8. The deferred integrate findings

The owner deferred the 1.2 integrate review's findings to 1.2.1 on 2026-11-10. Each is restated and
settled:

- **design-1-2, zoom-out-1-1 (medium): self-registration half done.** U32 made each module's
  `CONFIG_DEFAULTS`, `INIT_STEP` and `DOCTOR_CHECKS` the registry, but `doctor.py` still prints
  central lines and `load_config` still hard-codes defaults (`builder.stall_minutes`,
  `builder.max_subagent_calls`, `__init__.py:994-1017`) and its deep-merge list
  (`("astra", "ingest", "foreman", "builder", "reviewers", "brainstorm")`, `__init__.py:954`).
  Fixed: the defaults come only from the registered `CONFIG_DEFAULTS`; every registered key whose
  default is an object deep-merges; `doctor` prints the registered checks only. A module with
  nothing to register keeps its explicit empty line (`discover()` unchanged): removing ~24 of them
  touches two dozen files for no behaviour. The 1.2.1 keys register this way from the start.
- **zoom-out-1-2, zoom-out-1-3 (medium, low): two ingest writers.** `ingest` (`--unit`,
  `review.py:1193`) and `ingest_pr` (the spec PR, `review.py:1424`) each write findings and
  `ingested[]`. Settled without change: they read different sources (a unit's issue and PR, with
  rulings; the spec PR, without), and the shared parts already go through one reader. Merging them
  is more change than the duplication costs.
- **design-1-3, zoom-out-1-4 (medium): the early accept's lapse.** The landed rule is adopted as the
  design: an accept given below the cap holds its own round only. It lapses once a later round
  completes, once a later round holds an unsettled high or medium, or once a finding recorded into
  its round since (an ingested external one, a set finding) bars it; an accept ruled at the cap does
  not lapse. Once a verdict replaced the accept's `converged: by ruling <id>` mark, the accept never
  returns. No code change.
- **zoom-out-1-5 (medium): `STORE` and `CURRENT_ARGS` globals.** Settled without change:
  `atomic_write`'s write guard needs the running subcommand's store, and passing it to every one of
  the ~100 `atomic_write` calls is more change than the defect. The driver's assignment of
  `core.STORE` per store (`driver.py:286, 291`) is the one place the global is switched, and it is
  commented as such.
- **design-1-1 (medium): an interrupted launch has no `subagent_calls`.** `record_launch.finish`
  reads `subagent_calls` from the launch's `session_id` (`record_launch.py:122`), so an exit and a
  stall kill have it; `interrupt --launch` (`interrupt.py:36-45`) marks the launch `interrupted`
  without it. Fixed: `interrupt` reads it the same way.
- **design-1-4 (low): the judges' order.** The landed default order fable, opus, astra is adopted;
  the 1.2 design's order is superseded. No code change.
- **design-1-5 (low): the Scope-paths warning.** Superseded by `units.max_files` (section 6).
- **zoom-out-1-6, zoom-out-1-7 (low): rulings.** `decision.py` renders `**Ruling:**` text in two
  functions (`decision.py:94`, `:268`), and `review.py:1266`, `:1453` and `launch_builder.py:473`
  test a ruling with `startswith("**Ruling:**")`. Fixed: one renderer; every reader uses `ruling_of`.
- **zoom-out-1-8, zoom-out-1-9 (low): duplicates.** `inbox.kill_group` (SIGKILL of the notify hook's
  process group) reads like `__init__`'s SIGTERM group kill; renamed `sigkill_hook`. `driver.close_card`
  repeats `runcard`'s close; it calls a `runcard.close_card` both share.
- **zoom-out-1-10 (low): test helpers in production.** `traces.py`'s `trace_directory` and
  `assert_child_probe`, used only by `tests/unit/test_claude_traces.py`, move into that test file;
  `subagent_calls` stays in `traces.py`.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Chained phases run as unattended `bypassPermissions` sessions. | Only in a store the owner registered (typed), with the driver installed and `driver.chain` true; the 1.2 accepted residual is unchanged in kind, widened in phases. `doctor` prints `chain: on | off` per store. |
| A chained phase fails every tick. | The phase-aware twice-failed refusal (section 7.1) stops the handoff after two failed launches, as 1.2 does for `wave`; `driver reset` clears it. |
| A stopped or stalled plan review restarts with a fresh cap. | `next` prints `waiting review-plan: … stopped|stalled`; only the owner's typed run resumes it. |
| Idle sessions while heads wait for a merge. | The `wave` phase keeps `tick_trigger`; nothing to do starts nothing. |
| A builder writes the instructions its judges or reviewers read. | Every role reads instruction files at the approval commit (section 3.1). |
| An instruction file tells a builder to open a channel (Relay) that then carries text into the session. | SuperEGM reads nothing from it (anti-goal 3); the owner writes the file and grants the tool, and owns what the channel delivers. |
| A medium is deferred wrongly. | A zero-context triage goldfish answers the fields, not the foreman; `confirmed` needs a `file:line` at the head; regressions, test-delta, owner-only and external findings are ineligible; every deferral is listed in the review comment and undone by the owner's `finding upheld` ruling. |
| A config change breaks an in-flight handoff. | `rounds`, `triage`, `mode` and `instructions` are frozen per approval and carried by `--amend-units`; a cycle keeps the cap it opened with. |
| A cap of 3 moves work into cap rulings. | `review.rounds` and a spec's `Rounds:` raise it per project. |

## 10. SuperEGM's own configuration

In this design's commit, the repository's own `.superegm/config.json` changed `builder.model` from
`claude-opus-5-5` to `claude-sonnet-5-5` at effort `high`, and added `builder.tiers.difficult`
`claude-opus-5-5` at `medium` and `builder.tiers.easy` `claude-sonnet-5-5` at `medium`. Reviewers,
judges and the foreman are unchanged. These are this repository's choices, the owner's in the
brainstorm, not the plugin's defaults; the 1.2.1 build's launch record is what will show whether
they hold.

## 11. What is left to the builder

- The exact wording of each refusal, within the facts this design names.
- How `next` reads the store, as long as the table in section 7.1 is its whole behaviour.
- Test layout: one `tests/unit/test_u<NN>.py` per unit, as in 1.2.

## 12. Alternatives Considered

team: off (subagents not run; the owner brainstormed in conversation)

- **One key per audience** (`builder.orders_file`, `context_file`, …) for instructions. Rejected:
  every new audience would add a key and a code path; one list with `to` covers them all.
- **Instruction files read at the unit's base or the pull-request head.** Rejected: the head is the
  builder's to write, and a live config makes in-flight handoffs refuse; the approval commit is
  neither.
- **Triage rules in `config.json`.** Rejected by the owner: the rules decide what may merge with a
  known defect, so they belong in the reviewed, approved spec, frozen at approval.
- **Declarable triage fields and per-severity required lists.** Rejected: one known rule set needs
  four fixed fields; a general grammar costs a parser and a review lane for no user.
- **Triage that may unblock a high.** Rejected by the owner (anti-goal 1).
- **The foreman as triager.** Rejected: it drives its unit to land, so its answers would decide its
  own merge. The owner or the panel per finding was rejected too: that is the per-finding argument
  triage exists to end.
- **Keep the cap fixed at 5.** Rejected by the owner: the right number is per project.
- **Chain only in leavemealone.** Rejected by the owner: the phases after approval are mechanical in
  either mode; normal mode differs only in who answers a decision.
- **`approve-spec` registers the store.** Rejected: registration is the owner's opt-in to unattended
  sessions in that repository.
- **A changed-lines limit that refuses.** Rejected: the line count is known only after the build;
  it stays a planning target.
- **A `max_unit_deps` limit.** Rejected: no evidence ties the dependency count to relaunches, and a
  unit consuming three interfaces has no split that meets it.

## 13. Units

One row per unit, each within section 6's limits and 1.2's Size limits (S 3, M 8 scope paths); the
plan splits further by subsystem. Shared files are ordered after the table. Paths are under
`skills/plan/scripts/superegm/` unless they start with another top-level directory.
