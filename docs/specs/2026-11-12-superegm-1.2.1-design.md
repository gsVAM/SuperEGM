# SuperEGM 1.2.1 — design

Date: 2026-11-12. Status: brainstormed with the owner; in `/superegm:review-spec`.

Inputs: the owner's 1.2.1 change list (2026-11-12, given in conversation; this design is its record);
the 1.2 integrate review (`spec-2026-11-03-superegm-design-integrate-c1`, 0 high, 7 medium, 8 low,
deferred to 1.2.1 by the owner on 2026-11-10; §8 restates each finding it settles); the 1.0 build's
unit sizes and launch counts (§6); the 1.2 design,
[docs/specs/2026-11-03-superegm-design.md](2026-11-03-superegm-design.md), which this design amends
and does not restate. Where this design contradicts a passage of the 1.2 design, the passage is named
in §2.1 and this design wins. A term this design uses without defining it is the 1.2 design's (1.2
§2, Vocabulary). "1.2 §n" means the 1.2 design's section n; "§n" means this design's.

Owner's answers in the brainstorm and in this review: cap default 3, a spec's `Rounds:` line
overriding it for its own handoff; triage rules in the spec, highs never eligible; instructions for
builders, the foreman, reviewers and judges; the chain in both modes, off until the owner turns it on
per store; the size limits of §6; SuperEGM's own builders as in §10.

## 1. Intent

1.2 made SuperEGM runnable while the owner is away. Running it for real showed five places where
the owner still does work a machine could do, or where the fixed rules fit one project badly:

- **Every phase waits for a typed command**, even the ones that are mechanical once the spec is
  settled: plan, plan review, file, wave. The owner's judgement is spent on the spec; after
  approval it should be spent only on the decisions the workflow raises.
- **Five review rounds is too many for most work**, and the number is a constant.
- **Severity alone decides what blocks.** A medium that only a hand-forged in-process object can
  trigger, and that is easy to fix later, blocks a merge as hard as one an HTTP caller can trigger.
  Each project wants its own rule, and the rule must be written down before the build, not argued
  per finding.
- **Units are too big.** The 1.0 build, which had no body limit, filed unit bodies of 59–94 KB,
  22–52 files and 26–60 steps that took up to 11 launches each; a 24 KB, 8-file, 16-step unit merged
  first time. 1.2's 48 KiB body limit refuses every one of the large ones, but still passes a unit
  twice U01's size, a band no build has tried.

- **A narrowed panel can never finish.** A cycle's panel is fixed when it opens (1.2 §8). An owner
  who narrows the panel mid-cycle can only record the dropped reviewers `--not-run`, which
  makes every later round `not run`: the cycle neither converges nor reaches its cap, and two such
  rounds on one run card stop it as stalled (`review.py:176-186`, `:867-888`). The 1.2.1 spec's own
  review hit this at round 5.

And one place where the owner pastes the same text by hand: repository rules that every builder,
reviewer and judge should see (a house standard, a registration step) go into every issue body today.

1.2.1 fixes those, and settles the integrate review's deferred findings.

## 2. Goals, non-goals, anti-goals

Goals:

1. In a store the owner registered and set `driver.chain` to `true` in, from the approval commit at
   `origin/<base>` to the first builder launch, nothing waits for a typed command except a decision
   the workflow raises (§7). In normal mode file's Create is one (1.2 §13.2 point 4), so the
   normal-mode chain always stops once before the first wave.
2. The review round cap is configuration, default 3, and a spec may set its own (§4).
3. A spec may declare the patterns under which a medium stops blocking; on every pull-request head
   with an eligible medium a triage goldfish answers fixed triage fields, and a match defers the
   medium (§5).
4. One configuration list routes repository instruction files to builders, the foreman, reviewers
   and judges, frozen at approval and recorded on every dispatch (§3).
5. Unit size limits are configuration with defaults taken from the 1.0 build; the plan splits, and
   `scan` refuses (§6).
6. Each deferred integrate finding is fixed or settled in this design (§8).
7. An owner who re-types a spec review with a narrower panel (the config list or `--reviewers`)
   narrows the open cycle from its next unrecorded round, and those rounds can complete, converge
   and reach the cap (§4.1).

Non-goals:

- Merging. The driver never merges, in either mode; nothing in this design changes who merges.
- Triage on spec, plan and integrate reviews, and on highs. Those are unchanged.
- A per-finding override of the triage rules. A rule change is a spec change and needs a new
  approval.
- Registering a store, or turning its chain on, without the owner. `superegm register` and
  `driver.chain` stay the owner's.
- Remote builder hosts (the AgentCore line of work, builders launched on a hosted runtime). The
  launch contract is unchanged.

Anti-goals:

1. **A high never stops blocking by triage.** Triage covers mediums only; a high is never triaged
   or deferred.
2. **No instruction reaches an agent unrecorded.** Every dispatch whose brief or prompt carried an
   instruction file records the file and its blob sha in its own `instructions[]` field (§3.1). The
   isolation field still comes from the agent's `saw:` line alone, so a hook's exposure stays
   visible on its own.
3. **SuperEGM reads no instruction or ruling from chat or Relay.** An instruction file is a
   committed file; rulings come only from the `**Ruling:**` grammar from `config.owners`, or from the
   owner in an interactive session.

## 3. Repository instructions

### 3.1 The key

```json
"instructions": [
  {"file": ".superegm/rules.md", "to": ["builder", "foreman", "reviewers", "judges"]}
]
```

- `instructions` (default `[]`) is a list of entries. `file`: a path relative to the repository
  root, at most 8,192 bytes. `to`: a non-empty list from `builder`, `foreman`, `reviewers`,
  `judges`. Registered by the new module `skills/plan/scripts/superegm/instructions.py`.
- **Frozen at approval.** `approve-spec` copies the list into the approval entry with each file's
  12-hex blob sha at the approval commit, and refuses an entry whose file is absent there or over
  the size limit. It also copies each file into the store as
  `instructions/<blob sha>.json` (`file`, `sha`, `text`; a new store-level kind, beside
  `approvals`, and refuses a file that is not UTF-8), verified against the sha, so the frozen bytes outlive an amended or
  squash-merged approval commit that git later prunes; every reader below reads that copy. It prints each file whose sha differs from the spec's previous approval entry in
  `approvals/<slug>.json`, whatever its handoff, and every file with its sha when the spec has no
  earlier entry, so a merged edit to a file is seen when it takes effect. An `--amend-units` entry copies the list
  and its shas unchanged (§6), so the files are the same for the whole handoff. A later config edit
  governs the next approval only.
- **Where it is read.** Every role of an approved handoff reads each file by its frozen blob sha (the
  approval commit itself is not needed): a builder, the foreman, head reviewers, plan reviewers,
  integrate reviewers and every judge panel ruling on them. Nothing a builder commits on its branch
  or pull request reaches any brief. A spec review, its reviewers and any judge panel ruling on it
  read the config and the files at the commit `HEAD` names when the brief is rendered, whether or not
  the spec was approved before. The triage goldfish (§5.2) reads none: it answers fixed fields
  against the code.
- **One renderer.** `superegm instructions --role <role> (--handoff <id> | --spec <path> --review <id>
  --round <n>)` prints the section and is the only source of it. Exactly one of `--handoff` and
  `--spec` is required. `--handoff` reads the latest approval entry's frozen list and each file from
  its store copy by sha. `--spec` reads the list from the config committed at `HEAD` and the files there, refuses
  an entry whose file `HEAD` lacks, and stores the manifest it rendered (`[{file, sha}]`) and the
  rendered text in `reviews/<id>/instructions-<n>-<role>.json` (`{manifest, text}`; a name
  `round_numbers` does not glob, so `review record`'s first-record and cap checks,
  `review.py:501-529`, are unchanged). `--handoff` also takes `--runcard <card>` and stores
  `{approved_at, manifest, text}`, the approval entry it read included, on that card for that role.
  Only the first call for a round and role, or a card and role, renders; a later call (a retry, a
  second reviewer of the role) prints the stored text whatever `HEAD` or the latest approval is
  then, so a dispatch's manifest never changes. The section is one `# Repository instructions` heading, then each
  file addressed to that role, in list order, under a `## <file>` line, its text verbatim inside a
  fence of backticks one longer than the longest backtick run in the file (at least three), placed
  last in the brief or prompt. With no file addressed to the role it prints nothing. `launch-builder`
  and `prepare.py`'s `astra_brief` call the same function; the elephant and the foreman paste its
  output into the briefs they write. The section is part of the brief: an agent does not name it on
  its `saw:` line, and the isolation parser is unchanged. A spec review's Astra round n > 1 resumes
  the previous round's session only when the round's rendered manifest for Astra equals round
  n-1's (a file added, removed or changed, or a recipient changed, launches fresh and says so), an
  added condition to the resume test of `review_loop.md:107-110`; a resumed session would otherwise
  keep a file the round's record does not name.
- **Recorded.** Every dispatch stores `instructions: [{file, sha}]`; no caller passes it. For an
  approved handoff the recording helper copies the manifest stored on the dispatch's card for its
  role (a re-approval after the dispatch does not change it). A spec review's `review record` copies
  the manifest stored for that round and role. Neither resolves `HEAD` or the latest approval again.
  A judge panel renders once, when it opens: from its parent card's handoff (`__init__.py:482-486`),
  that handoff's frozen list, else the parent card's artifact as the spec at `HEAD`; `render_brief`
  stores the manifest and text on the panel, and every later panel round (`judges.py:245`, `:425`)
  reuses the stored text. It lands on the builder's launch entry, each review round's reviewer record, the
  judge panel's member record, and the wave's record of the foreman's own dispatch in
  `foreman/<unit>.json`; an empty list when none was addressed.
- **Tools stay where they are.** A file cannot grant a tool: a command it asks the builder to run
  still needs a `builder.allowed_tools` entry the owner adds.
- `pr_block_file` is unchanged: it is text for the pull request body, read at the launch's ref, not
  an instruction.
- **Off the machine.** The Astra lane (the Codex-backed reviewer, 1.2 §8) and the `astra` judge
  member send their brief to the Codex vendor, so a file addressed to `reviewers` or `judges` goes
  there too; `docs/privacy.md` says so.

### 3.2 First user

The owner's first file is addressed to `builder` only: a one-time registration command at the start
of each builder session (Relay, the owner's agent-messaging service). It is the owner's file, not
part of this design; the owner adds the command's prefix to `builder.allowed_tools`. Subagents
(reviewers, judges, the foreman) are never addressed with it: a registration names a session's
process. The risk of what such a channel then delivers is §9's.

## 4. The review round cap

- `review.rounds`: an integer 1–10, default **3**, registered by `review.py`. It replaces the
  constant `CAP = 5` (`skills/plan/scripts/superegm/review.py:52`) for every review kind: spec, plan,
  head and integrate. The judge panel's own `CAP = 5` (`skills/plan/scripts/superegm/judges.py:25`)
  is unchanged. A value outside 1–10 is refused by the command that reads it, naming the key.
- A spec may carry one `Rounds: <n>` line, `n` 1–10, before its first H2. `approve-spec` parses it,
  refuses any other value and a second `Rounds:` line before the first H2, each with the line, and
  freezes the value in the approval entry; with no such line it freezes the live `review.rounds`. A
  `Rounds:` line after the first H2 is prose. The frozen value governs that handoff's plan, head and
  integrate reviews. It cannot govern the spec's own review, which runs before approval under
  `review.rounds`.
- A cycle stores `cap` when it opens and keeps it; a record without one (opened under 1.2.0) reads
  as 5.
- The rest is unchanged, kind by kind: one more round per `continue` ruling; at the cap a spec, plan
  or integrate review is ruled continue, accept or stop, a head continue, stop or redesign (its
  accept stays refused, `review.py:1650`); an early accept below the cap works as in 1.2.

### 4.1 A narrowed panel

- Spec reviews only. The owner narrows an open spec cycle's panel the way they choose a panel
  today: by the panel the invocation carries, `config.reviewers.spec` or the invocation's
  `--reviewers` (`review_loop.md` §1 step 2). A re-typed `/superegm:review-spec` already passes that
  panel to `review open`, which resumes the open cycle and ignores it (`review.py:436-441`). In
  1.2.1 the resume compares it with the panel of the cycle's next round.
- The next round is the first round with no record yet; its current panel is the reviewers of the
  last entry of the review's `panels` list whose `from_round` is at most that round, else the
  cycle's panel (`review["reviewers"]`), so a 1.2.0 record reads as before. When the given panel,
  `astra` aside, is a proper subset of that current panel's non-`astra` reviewers and still starts
  with `design` (`FIRST`), the resume appends `{"from_round": <n>, "reviewers": <given panel + the
  cycle's Astra lane>}` to `panels` and journals the narrowing. Any other given panel (wider,
  overlapping, or equal) changes nothing, so a panel never widens; a given panel not starting with
  `design` is refused before the resume, as in 1.2 (`review.py:424-425`).
- Every resume of a spec cycle prints a second line after the id, changed or not (other kinds print
  the id alone, as in 1.2): `panel <a,b,astra> from round <n>`, the next
  round's panel, followed by `(unchanged: <reason>)` when a given panel that differs was not taken.
  The review loop dispatches that line's panel, not the one the invocation carried
  (`review_loop.md` §1 step 4 and §2; `skills/review-spec/SKILL.md:91-92`, `:110`).
- `derive_what_ran` and `review record`'s refusal (`review.py:509`) read the round's panel, so a
  dropped reviewer needs no `--not-run` record and a round of the narrowed panel can complete.
- Convergence, the cap, the stall rule and `review status` are unchanged: they count `completed`
  rounds, which a narrowed round now can be. A dropped reviewer's findings in earlier rounds keep
  their dispositions; the clean rule reads the latest round only, as in 1.2.
- Plan, head and integrate reviews keep 1.2's fixed panel: review-plan resumes a cycle without
  calling `review open` (`review_plan.py:71-84`), the wave fixes a head's panel in its run card
  (`foreman_brief.md:38`), and integrate runs one round (`skills/integrate/SKILL.md:47-64`).

## 5. Medium triage

### 5.1 In the spec

Triage is declared by a spec's optional triage section: the first H2, outside a fenced block, whose
text is exactly `Triage`. No section: triage is off, and the 1.2 rule (a high or medium blocks until
fixed or ruled) stands. Inside the section the parser reads one `Unblock:` line and the run of `- `
lines directly after it; the run ends at the first other line, and any line outside it is prose and
ignored.

```markdown
## Triage

Unblock:
- reach: forged, later: easy
- critical: no, later: easy, verified: confirmed
```

- The fields are fixed, and every triage answers all four:
  - **reach** `external | agent | config | forged`: can an HTTP caller, an agent action, or a
    plausible configuration mistake trigger it, or only a hand-forged in-process object?
  - **later** `easy | migration | version`: easy to fix later, or does the fix need a migration or a
    new declaration version?
  - **critical** `yes | no`: on the critical path with serious ramifications?
  - **verified**: `confirmed <file:line>` (the defect is at that line) or `refuted <reason>` (the
    triager finds no defect), matched as `confirmed` or `refuted`.
- `Unblock`: patterns, numbered 1, 2, … in order, each one or more `field: value` pairs separated by
  `, ` that must all hold. A pattern applies to mediums only.
- `approve-spec` parses the section and freezes the patterns into the approval entry. It refuses,
  with the line at fault: an unknown field or value, a field repeated in one pattern, an empty
  pattern, a second `Unblock:` line, and a section with no `Unblock:` line or no pattern. The wave
  reads the frozen copy only; editing the section needs a new approval.
- The brainstorming skill offers the section and writes it with the owner. Spec review checks it:
  `structural` the grammar, `design` whether the patterns are safe for the project.

### 5.2 On a pull-request head

- **Eligible.** A panel medium of the round that is not a regression, not a `test-delta:` finding,
  not named in an `owner:` line, and not an `external:<login>` finding, in a unit whose triage the
  owner has not turned off by an undo (below). Every other finding blocks as in 1.2.
  `superegm review triage --review <id> --round <n> --eligible` prints the eligible fids.
- **Who triages.** When the frozen triage is on and the round has an eligible medium, after the head
  round is recorded and before `review post`, the foreman dispatches one `triage` goldfish (a new
  zero-context, read-only adapter, `superegm:triage`) with the four field definitions and every
  eligible medium of the round, never the patterns. Its adapter forbids reading the spec or anything
  under `docs/specs/`. It runs with the head reviewers' model and effort. It reads the code at the
  head in the review worktree and writes one line per finding, with `verified` last and taking the
  rest of the line:
  `<fid> | reach: <v> | later: <v> | critical: <v> | verified: confirmed <file:line>`, or
  `<fid> | reach: <v> | later: <v> | critical: <v> | verified: refuted <reason>`.
  The foreman records the reply verbatim with `superegm review triage --review <id> --round <n>
  --file <path> --isolation <…> --model <…> --effort <…> --runcard <card>`, as it records a
  reviewer's findings file today; it neither writes nor edits a value.
- **Refusals.** Triage off; a finding not eligible; an eligible medium with no line; an unknown
  value; a missing field; a `confirmed` whose `<file:line>` does not exist at the round's head; a
  second triage of the round. One bad line refuses the whole file, and a refused file records
  nothing. On a refusal or a failed dispatch, the foreman dispatches the triage goldfish once more;
  a second failure of either kind posts the round with those mediums blocking, as with triage off.
- **Deferred.** An eligible medium whose triage matches a pattern no longer blocks: it gets the
  disposition `deferred: triage <n>`, `n` the first matching pattern, one journal line, one row in
  `foreman/<unit>.json.followups[]` (`fid`, round, claim, triage, pattern) written when the round
  posts, by `count_posted` (`review.py:1593`, recovery included, once per fid and round), so a round
  that never posts (not run, or superseded) leaves no row, and the review comment
  `render_comment` builds lists it under **Deferred by triage**. The builder may still fix it.
- **Each round.** A medium re-reported in a later round is triaged again on the new head; a
  deferral is not carried forward. That is intended: the head changed.
- **Undo.** The owner posts `**Ruling:** <fid> finding upheld (fix it)` by hand on the unit's
  issue, where every ruling reader looks (`collect.py:553`, `status.py:416-419`), naming a
  deferred medium of the unit's latest posted round. `tick_trigger` sees it as any ruling, and the
  wave session's ruling path (`skills/wave/references/rulings.md`) runs `superegm decision rule
  --unit <U> --ruling '<fid> finding upheld' --by <login> --posted <comment id>` without
  `--decision`. Today that drops an `upheld` no open decision names (`decision.py:776-787`); in
  1.2.1 an `upheld` on a triage-deferred fid is checked as the undo first, before `decision rule`
  looks for a decision by fid (`fid_decisions`, `decision.py:816-823`), so it never binds to an older
  point-1 decision. On a fid of the unit's latest posted round it is applied there, with no new
  dispatch and no `collect`: it clears the disposition to none (every unsettled test reads
  `disposition is None`, `review.py:871`, `:910`, `:954`), sets `undone_by: <comment id>` on the
  finding itself, records the ruling in `foreman/<unit>.json.rulings[]` as a standalone entry
  (`kind: undo`, `decision: null`, `fid`, `by`, `posted`, `ruling`, `posted_at` the verified
  comment's `updated_at` or `created_at`, `at`; `decision: null` keeps every reader that compares
  `r["decision"]`, `decision.py:445`, `:742`, `:746`, `:860`, false on it, and `posted_at` is what
  `collect.recorded_times`, `collect.py:483-488`, reads, so a `fixed` reply must still follow the
  undo after its comment is edited or deleted; `recorded_rulings` returns the entry with no
  decision, where today it skips an entry without one, `decision.py:103-106`), drops the follow-up row,
  journals, and the finding is an unsettled medium of that round again, so `evaluate` no longer
  reads the head clean and an accept given on the round lapses, as a new blocker lapses one
  (`early_accept_lapsed`, `review.py:935`). The undo rewrites the unit's latest posted
  `foreman/<unit>.json` entry as ingest does (`review.py:1366-1369`): a `clean` outcome becomes
  `revise`, or `cap-reached` at the cap, with `rewritten_from: clean`, so `latest_clean` and
  `ready_again` (`launch.py:109-122`) read it and the next wave session sends the unit to revision
  or to the cap decision. Triage is off for that unit's remaining rounds, so the re-reported
  finding cannot be deferred again. `decision rule` refuses an undo on a deferral of an earlier round (the head
  has moved and a later round was reviewed on it), on a stopped unit (`foreman.stopped`, or the `labels.stopped` label on its issue, the test `launch` itself uses, `launch.py:73-75`, which a stop writes before the record, `decision.py:488`; `foreman.stopped` is set by a
  stop or redesign, `decision.py:478-520`; wave ignores a stopped unit's ruling events,
  `skills/wave/SKILL.md:113-115`, and launch never revises it, `launch.py:73-83`), and on a unit
  whose pull request is merged or closed (`gh pr view <n> --json state`, checked when the undo is applied; landed alone is not
  enough, since it also needs the issue closed, `status.py:387-411`, and a merged pull request with
  an open issue cannot take a revision); in every case the follow-up
  row stays and the owner files it as follow-up work. The record is authoritative everywhere. An
  accepted undo binds as a recorded ruling, so editing or deleting its comment changes nothing
  (`overridden_comments`, `deleted_rulings`, `decision.py:192-241`, read `rulings[]`).
  `binding_rulings` (`decision.py:129`) takes a new `deferred` parameter, the fids of the record's
  `followups[]`, and drops a live `upheld` comment naming one of them: a refused undo leaves its
  follow-up row, so it never reaches `collect` (`collect.py:553`, `:620-621`) or the builder prompt
  (`overridden_comments`, called by `launch_builder.py:464` with the foreman record, passes it from
  that record), and never blocks a later round.
- A medium triaged `refuted` matches a pattern only if the pattern names `verified: refuted`; no
  example does. A refuted medium that matches no pattern blocks as in 1.2; the builder may contest
  it (point 1) like any finding.
- A clean outcome needs every high and medium fixed, ruled, or deferred by triage.
- `close` lists the handoff's follow-ups in its closing note. `integrate` gives them to the
  integrate reviewers as known: a reviewer reports one only where the integrated code makes it worse
  than its row says.

## 6. Unit size

```json
"units": {"max_body_kb": 25, "max_files": 10, "max_steps": 16}
```

- **Limits.** A unit's rendered body at most `max_body_kb` × 1024 bytes (25,600), at most
  `max_files` `Scope paths`, at most `max_steps` steps. Registered by `scan.py`; each value is a
  positive integer, `max_body_kb` at most 48 (so a body stays under 1.2's 49,152 bytes and GitHub's
  65,536-character issue body), and `max_files` at least 8 (Size M's limit). The limits are read live at each
  `scan`, never frozen. `scan` checks unfiled units only; a filed unit is never checked again. A
  lowered limit can refuse a reviewed plan's unfiled unit; the owner then re-plans (§9). The body
  limit applies to unit bodies only; `BODY_LIMIT = 49_152`
  (`skills/plan/scripts/superegm/__init__.py:65`) stays the limit of titles, the tracking issue and
  comments (`scan_text`). Size's parse-time limits (`SIZE_LIMIT`, `__init__.py:64`: S 3, M 8, L

- **Target.** `skills/plan/references/writing_plans.md` aims each unit at one behaviour reviewable as
  one pull request of about 600 changed lines. It is guidance; no key holds it and nothing refuses on
  it.
- **The plan splits only through the spec.** Every plan unit is one row of the spec's `## Units`
  table (`skills/plan/SKILL.md:93`), so a unit over a limit needs new rows: the plan stops for

  `units.*` raise them per project.
- **Frozen fields carried.** An `--amend-units` entry copies every frozen field (`rounds`, `triage`,

- **Approved under 1.2.0.** An approval entry without a frozen field reads: `rounds` 5, `triage`

### 7.2 Decisions under the chain

The decision points are 1.2 §13.2's four (point 1 a contested or declined high or medium; point 2 a
review at its cap; point 3 an open question, a blocked builder or a launch that ended without a
head; point 4 the owner's approval of a converged spec, and file's Create, in normal mode) and
1.2 §17 U35's accept below the cap, called point 5 here.

- **Before filing (plan, review-plan, file).** A headless phase cannot ask. Where it would ask the
  owner in normal mode (the plan's point 3, review-plan's per-round accept question, a contested
  high or medium, a review at its cap, a stall) or must stop in either mode (a split needing
  `--amend-units`), it runs `superegm next wait --phase <phase> --question <text> --runcard <card>`,
  which writes the record `chain/<handoff>.json` (`phase`, `question`, `since`) and closes the card
  it is given, and exits. Under the driver, review-plan's start question is not asked: the chain
  chose to start. A normal-mode file is never launched (§7.1). The inbox and the notify hook carry
  the question.
- **The owner's answer.** The owner types the phase's skill in an interactive session. Finding a
  wait record, the skill opens its card with `runcard open --mode normal` whatever the frozen mode,
  asks the owner the record's question directly, with no new panel, records the answer as a
  normal-mode run does (`review settle --owner`, `decide` by the owner) and runs the phase on.
  `decide` stores its card's mode on the decision (`decide.py:50`), and `scan`'s ruler check
  (`scan.py:129-133`) refuses an owner's answer only when the decision's stored mode is
  `leavemealone` (a decision without one reads the frozen mode, else `config.mode`);
  `review settle` already reads the card's mode (`review.py:673-677`). While its card is open the tick skips the handoff. At its end the
  session runs `superegm next clear`, which removes the record when `next`, read without it, prints
  anything other than the record's phase; otherwise the record stays and the tick keeps skipping the
  handoff.
- **After filing (wave).** Normal mode: the headless wave opens points 1, 2, 3 and 5 as `decision
  open` records (as the leavemealone wave does) instead of asking, and exits; the owner answers in
  the inbox or with a `**Ruling:**` comment, which the next tick's `tick_trigger` sees. Point 4 does
  not arise after filing.
- **Leavemealone** routes to the judges only what 1.2 routes to them: before filing, the panel rules
  as the plan and review-plan skills do today, and file creates; after filing, the wave as today.
  Owner-only outcomes (a `test-delta:` finding, an `owner:` line, a split needing `--amend-units`)
  and every question a panel leaves unconverged become a wait record or an open decision, never a
  new panel on the next tick.
- The run cards, journal lines and records are the same in both modes; only who answers differs.
- Merging stays the owner's. Clean heads wait for the owner's merge as in 1.2.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Chained phases run as unattended `bypassPermissions` sessions. | Only in a store the owner registered (typed) and set `driver.chain` to `true` in, with the driver installed; a store registered under 1.2 keeps 1.2's driver. `doctor` prints `chain: on` or `chain: off` for this repository's store; another registered store shows it in its own repository. |
| A chained phase fails, or exits without moving on, every tick. | A launch that leaves `next` unchanged is a failed launch; two consecutive failures stop the handoff (§7.1), as 1.2 does for `wave`; a typed run or `driver reset` clears it. |
| A stopped or stalled plan review restarts with a fresh cap. | `next` prints `waiting review-plan: … stopped`; a driven session that meets a stall writes a wait record; only the owner's typed run resumes either. |
| Idle sessions while heads wait for a merge. | The `wave` phase keeps `tick_trigger`; nothing to do starts nothing. |
| A builder writes the instructions its judges or reviewers read. | Every role of a handoff reads instruction files by their frozen blob shas (§3.1); `approve-spec` prints each file that changed since the previous approval. |

## 12. Alternatives Considered

team: off (the brainstorm's cartographer and team subagents were not run; the owner brainstormed in
conversation)

- **One key per audience** (`builder.orders_file`, `context_file`, …) for instructions. Rejected:
  every new audience would add a key and a code path; one list with `to` covers them all.
- **Instruction files read at the unit's base or the pull-request head.** Rejected: the head is the
  builder's to write, and the base moves as units land, so a builder's merged edit would reach later
  units' reviewers; the frozen shas are neither.
- **Triage rules in `config.json`.** Rejected by the owner: the rules decide what may merge with a
  known defect, so they belong in the reviewed, approved spec, frozen at approval.
- **Declarable triage fields and per-severity required lists.** Rejected: one known rule set needs
  four fixed fields; a general grammar costs a parser and a review lane for no user.
- **Triage that may unblock a high.** Rejected by the owner (anti-goal 1).
- **The foreman as triager.** Rejected: it drives its unit to land, so its answers would decide its
  own merge. The owner or the panel per finding was rejected too: that is the per-finding argument
  triage exists to end.
- **Head reviewers answer the fields on their own rows.** Rejected: the reviewer who found a medium
  would grade its own finding's reach, and `verified` is worth something only from a second reader.
- **A command that re-fixes a cycle's panel** (`review panel --drop`). Rejected: the config list is
  already the owner's panel choice; a second place to set it would need its own ruling grammar.
- **Reviewers recorded `--not-run` with an owner reason count as run.** Rejected: an owner reason on
  each round per dropped reviewer is busywork, and `not run` would stop meaning a reviewer failed.
- **Keep the cap fixed at 5.** Rejected by the owner: the right number is per project.
- **Chain only in leavemealone.** Rejected by the owner: the phases after approval are mechanical in
  either mode; normal mode differs only in who answers a decision, and stops once at file's Create.
- **A normal-mode chain that files without asking.** Rejected: Create is the owner's decision in
  normal mode (point 4); skipping it would make the chain change the mode.
- **The chain on by default.** Rejected by the owner: a store registered under 1.2 was registered
  for driven waves only, so chaining must be the owner's choice per store.
- **`approve-spec` registers the store.** Rejected: registration is the owner's opt-in to unattended
  sessions in that repository.
- **A changed-lines limit that refuses.** Rejected: the line count is known only after the build;
  it stays planning guidance.
- **A `max_unit_deps` limit.** Rejected: no evidence ties the dependency count to relaunches, and a
  unit consuming three interfaces has no split that meets it.
