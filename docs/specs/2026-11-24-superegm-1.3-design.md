## 1. Intent

1.3 is about **not doing the same work twice, and not being misled by work that is already
done.** In the words of the owner's README, an agent that reads a stale TODO, an old plan or an
out-of-date line in `CLAUDE.md` treats it as an instruction.

The 1.2.1 build showed the same problem inside SuperEGM:
- Six handoffs in the store have no `closed_at`, and tracking issues #21, #35, #117 and #193 are
  open for work that merged long ago.
- Units lost their `launched` mark because one command overwrote another's write (§3.1).
- Settled findings came back as new highs round after round (§3.5).
- Eleven units hit their round cap and merged with findings left open. Those findings live only
  in retro issues, and 55 of 59 are still true at 8b7032e.

1.3 has three parts, built in this order:

1. **Fix what the 1.3 wave itself runs on** (§3). The store, GitHub calls, the foreman's gate,
   rulings, respec and the inbox all carry known defects, and the 1.3 wave would hit them again.
2. **Tracks** (§4): for every piece of work, whether it is finished, where it came from and what
   shows it.
3. **The sweep** (§5): a skill that finds stale TODOs, specs and rules-file lines. A separate
   fresh agent checks each one against the code and git history before anything is called stale.

## 2. Goals, non-goals, anti-goals

Goals:
1. No change to `state.json`, a unit's `foreman/<U>.json` or the track file is lost to a
   concurrent helper command: it is merged, or the later command refuses and is run again (§3.1).
2. A transient GitHub error never ends a helper command with a traceback (§3.2).
3. A unit whose Definition of done needs the full test suite can pass the foreman's gate (§3.3).
4. Every open or partly fixed row of the inputs file is owned by a named unit, or listed in §3.11
   with a reason. §3.12 is the complete list.
5. Every handoff, unit and respec has a track whose status follows from what the store records,
   and the owner can add tracks for any other work. A finished or dropped track carries evidence
   built only from recorded facts (§4).
6. `/superegm:sweep` reports stale material with evidence and changes nothing on its own (§5).
7. The 1.3 README says what 1.3 ships, and nothing it does not (§7).

Non-goals:
- Sharing tracks across machines or people. Tracks stay in the store, by the owner's choice.
- Putting tracks into a builder's prompt. The session that decides what work to start is the
  owner's elephant session, and that is the session tracks serve (§4.4).
- Removing stale material automatically. The sweep reports; the owner decides (§5.3).
- Turning triage-deferred follow-ups into tracks. `close` already lists them in its closing note
  (1.2.1 §5.2); the owner adds a `fix` track by hand for one they want to follow.
- Merging concurrent writes of the round files, `review.json` and `launches/<U>.json`. No write
  to them was lost in 1.2.1; §9 records the residual.
- The rows §3.11 lists, each with its reason.

Anti-goals:
1. **No fix widens what an unattended builder may run.** Lessons 15, 51, 52 and 53 asked for a
   looser allow-list. §3.7 instead removes the `git push` prefix entries and documents the commands
   that exist.
2. **No text by someone other than the builder or an owner reaches a builder's prompt**, and no
   edited comment does (§3.7).
3. **No contest is dropped by matching its wording.** §3.5 drops a contest only when its fid, or
   the fid it derives from, is settled.
4. **No track is shown as done or dropped without evidence**, and the helper never states a fact
   the store does not record (§4.1).
5. **The sweep never edits, deletes or commits anything** (§5.3).

## 3. Fixes the 1.3 wave runs on

### 3.1 The store: no lost writes

**The defect.** `status --wait` (`status.py:170-194`) loads `state.json`, waits up to 30 minutes,
then saves the copy it loaded. `save_state` replaces the whole file (`__init__.py:1791`), so any
launch mark, ruling or settlement written meanwhile is lost. The comment at `status.py:188` says
the opposite. This explains L48, L49 and L56. Any command that loads `state.json` or
`foreman/<U>.json`, changes it and saves it can lose another command's write the same way.

**The fix: the save merges.** The callers do not change; `load_state`, `save_state`,
`load_foreman` and `save_foreman` do.
- `load_state` and `load_foreman` keep, per file and per process, a copy of what they loaded: the
  base.
- `save_state` and `save_foreman` take an exclusive `fcntl.flock` on a lock file beside the data
  file, read the file fresh, merge, write atomically and release the lock. The lock file is created
  once and never replaced, the idiom of `driver.store_lock` (`driver.py:492-544`): a lock file
  that `atomic_write` renamed over would let a second holder in on the new inode. The lock is held
  only inside the save, never across a wait, a model call or a GitHub call, and one save takes one
  lock, so no command holds two.
- The merge compares three copies, key by key: the base, the caller's copy and the fresh file. The
  keys are the top-level keys, and in `state.json` each `units.<U>.<key>`.
  - A key only the caller changed takes the caller's value. A key only another command changed
    keeps the fresh value. A key both set to the same value is that value.
  - A list both sides only appended to, from the base, becomes the base, then the fresh additions,
    then the caller's.
  - Anything else is a conflict: the save writes nothing and refuses with
    `concurrent change to <key>: nothing written; run the command again`. The command's own
    refusals run again on the next attempt, on fresh data.
  - With no base (a file the process never loaded), the save writes the caller's copy, as today.
- After a successful save, the saved file becomes the new base.
- `status --wait` therefore needs no special code: its changes merge with a launch mark written
  during its wait. The wrong comment at `status.py:188` is corrected.
- **`collect`** keeps its hold-and-restore of the foreman file across the DoD runs
  (`collect.py:386-391, 674-685`): that restore is the guard against a builder's test editing the
  store. To stop it erasing a legitimate write, `collect` writes a marker, `collecting.<U>` beside
  the foreman file, holding its process id, before the DoD runs, and removes it after the restore.
  While a live marker exists, `save_foreman` for that unit from any other process refuses with
  `collect running on <U>: run again when it ends`. A marker whose process is gone is ignored and
  removed.
- The track file (§4.1) is saved the same way.

**Acceptance.**
- One process in `status --wait` and one writing a launch mark during the wait: both changes land.
- Two processes appending rulings to one unit's `rulings[]`: both land, in order.
- Two processes setting the same key to different values: one lands, the other refuses with the
  conflict line and writes nothing.
- An owner's `decision rule` while that unit's `collect` runs refuses with the `collect running`
  line, and lands when typed again after.
- A store written by 1.2.1, with no lock files, opens and is changed without error.

### 3.2 GitHub calls

Input: L5, L41.
- `gh_json` retries an HTTP 502, 503 or 504, or a connection reset, up to three times with backoff
  of 1, 4 and 16 seconds. Rate limits keep their own retry (`gh_retry`). A 4xx is never retried.
- A `GhError` that escapes a subcommand prints one line, `gh: <the error>`, and exits non-zero, as
  a `HandoffError` does. It never prints a traceback.
- `discover_pr` keeps its first lookup, the GraphQL `closedByPullRequestsReferences` query
  (`__init__.py:2044-2056`), whose result is a match as today. Its second lookup becomes
  `gh pr list --head <the unit's branch> --state all`, whose result is a `--watch` candidate, as a
  head-branch pull request without closing references is today (`__init__.py:2070-2072`). The
  1,000-pull-request list is removed: a unit's pull request is always on its own branch.

### 3.3 The full suite and the foreman's time limits

Input: L3, L6, L14, L17, L18, #242 foreman-5-1 (high).

The full suite takes about 11 minutes. One `collect` call is capped at 9 minutes, because the
foreman is a subagent that must run `collect` in the foreground (`docs/claude.md`, "Background
commands": a subagent's background command dies when it returns) under the Bash tool's 10-minute
limit. So a DoD item that runs the whole suite can never pass, and no cap fixes that.

The fix needs no new config key:
- **The full suite is never a `Run` DoD item.** The plan grammar already has `CI green on the
  head`, which `collect` reads and never re-runs (`graph.py:25`,
  `skills/plan/references/handoff_plan.md:102`), and `collect` already raises a high when CI is not
  green on the head (`collect.py:568-569`). The plan skill and `writing_plans.md` say: a unit's own
  test file is a `Run` item, and the full suite is covered by `CI green on the head`.
- The builder orders say the same for the builder's own runs: before a push the builder runs its
  unit's tests, and the full suite is CI's (`builder_orders.md:12,28` today tell it to run the full
  suite, which also exceeds a Bash call's limit).
- **"Green" means a check ran.** `GREEN_CONCLUSIONS` (`__init__.py:72`) counts `neutral` and
  `skipped` as green. A head whose checks are all `neutral` or `skipped`, or that has none, is not
  green, for the DoD item and for `collect`'s CI high.
- `foreman.run_timeout_minutes` keeps its bound of at most 9.
- `builder.stall_minutes` defaults to 60 (L3).
- The foreman brief and `skills/wave/SKILL.md` say what the wave does today: the foreman runs in the
  background beside `status --wait`, and `collect` itself runs in the foreground, never with
  `run_in_background` (L6, L14).

### 3.4 Recovering a round

Input: L7, L8, L19, L43, L55, #240 codebase-details-5-1.
- `review record --sha256`, which only a head takes, refuses anything but the full 40-hex commit
  sha. The `prepared:` line prints the full sha (L43, L55).
- The foreman brief says that a `collect` that fails after the panel ran is run again on the same
  prepared round, which stays `prepared` until `collect` succeeds. `--not-run` is only for a round
  whose panel did not run (L19).
- The brief tells the foreman to pass `model` and `effort` on every Agent call (L7), and its
  promise about deviation evidence says exactly what `decision.py`'s check counts (#240
  codebase-details-5-1). `collect` prints each finding's line, not only a count (L8).

### 3.5 Settled findings stay settled

Input: L24, L25, L39.
- `collect` drops a builder's contest of a fid when that fid, or the fid it derives from, is
  already settled by an owner's or the judges' ruling. Example: a `foreman-*` finding derived from
  `dod-<n>` that the owner ruled `allowed`. The match is by fid and derivation, never by wording
  (anti-goal 3).
- An owner's `test-delta <file> allowed` also widens Scope for that file, so the file does not come
  back as a scope high (L25).
- A test-delta settlement is keyed by the file, the kind, the qualified name of the enclosing test
  (the nearest enclosing `def test_*`, with its class when it has one, or `<module>`), and the
  removed or weakened line's text with whitespace collapsed. A merge of main or a line shift does
  not re-raise it, and a different change in the same test is not covered by it. A settlement in a
  1.2.1 record, keyed by base commit and line, is still honoured on that key. A judges' overrule
  carries the same way (L39).

### 3.6 Rulings

Input: L34, L42, L49.
- A `decision rule` refusal that lacks a fid says so: `missing <fid>: write "<fid> finding
  overruled"`.
- `decision withdraw --unit <U> --decision <id> --reason <text>` closes an owner's mistaken pending
  decision. It appends to the unit's `rulings[]` an entry with `ruling: "withdrawn"`, `kind:
  "withdrawn"`, `decision`, `reason`, `by: "owner"` and `at`. `report.pending_decisions` treats a
  withdrawn decision as closed whatever its point, and every reader that indexes `r["ruling"]`
  finds a value. It is refused on a decision that already has a ruling. Typed without `--runcard`,
  it opens and closes its own `decision` card, as `approve-spec --void` does (L49).
- A point-1 `decision rule` on a finding settles that finding itself, so the separate
  `review settle --owner --posted` step is no longer needed; it still works (L42).

### 3.7 Builder launch, orders and what reaches the prompt

Input: L1, L9, L13, L15, L16, L51, L52, L53, L54.

**The push.** The allow-list entry `Bash(git push origin <branch>:*)` is a prefix, so it also
matches `git push origin <branch>:main`; a prefix entry cannot exclude a refspec
(`docs/claude.md`). In the elephant's call:
- `launch-builder` writes a `superegm-push` script into the launch's `_bin` directory, next to the
  `gh` shim. It ignores its arguments and runs
  `git push --no-follow-tags origin HEAD:refs/heads/<branch>`, the branch fixed at launch. It does
  not pass `-u`, so it writes nothing into the repository's shared `.git/config`.
- The allow-list carries that script's absolute path in place of every `git push` entry, and the
  orders say `{{push}}`.
- This removes the typed route to another ref. It does not make one impossible: a builder can still
  run a script through `pytest` or a DoD command's first word with its credentials in the
  environment. Branch protection on the base branch stays the guard (§9).

**The orders** (`skills/wave/references/builder_orders.md`) gain one section, filled at each launch:
- `{{allowed}}`: the allow-list `launch-builder` wrote for this launch, one entry per line.
- The rule: one command per Bash call, with no pipes, `;`, `&&`, `||` or heredocs.
- Comments and PR bodies are written to a file with Write and posted with one `gh … --body-file`
  call (L51 to L53).
- The check for an existing PR is `gh pr view <branch>` (L54).
- Every file the builder changes, tests included, gets its `<what>` in the file's provenance header
  (L9; `docs/reference/invariants.md`).
- A Step whose test passes before any change is posted as a deviation; it is never committed as an
  empty `feat` commit (L16: the elephant's call keeps the deviation path, and `tdd-order` is
  unchanged).

**What reaches the prompt.** Today `prompt_text` carries `**Deviation (…):**` comments from any
author, `**Seam:**` from the builder, `**Decision D<n>:**` and `**Ruling:**` from owners
(`launch_builder.py:48,834-841`), and every PR review body from any login but the builder
(`launch_builder.py:860-863`). In 1.3:
- The per-form author rules stay. `**Deviation (…):**` narrows to the builder's identity and
  `config.owners`. PR review bodies narrow to `config.owners`.
- A new form, `**Note:** <text>`, from `config.owners` only, is carried into every later launch
  prompt of that unit under `# Owner notes`, oldest first (L13).
- Any carried comment or review whose `updated_at` differs from its `created_at` is left out and
  journaled as `<form> ignored: edited`. GitHub lets an account with write access edit another
  user's comment; an author who wants to change one posts a new one. A recorded ruling is still
  replaced by its record, as today.
- Anything left out by these rules is journaled as `<form> ignored: <login> is not the builder or
  an owner`.

**Managed settings in the profile.** On 2026-11-24 the builder profile's `remote-settings.json`,
the organisation's managed settings that Claude Code syncs, held the keys `enabledPlugins`,
`extraKnownMarketplaces` and `hooks`. Managed settings apply whatever `--setting-sources` says, so
those hooks run inside every builder, and `doctor` checks only `settings.json`.
- A new function, `managed_settings()`, reads `remote-settings.json` and returns its plugin names
  and hook events. `managed_plugins()` and the refusals built on it (`plugins_held`,
  `profile_problem`) do not change.
- Each launch records the result in a new `managed_settings` field of `_plugins.json`.
- `doctor` gains an informational `managed:` line printing the same names: the owner cannot remove
  managed settings. §9 records the risk.

**The builder's login.** No on-disk check: on macOS the login is kept in the Keychain. `doctor
--probe` (`doctor.py:59-96`) already runs one headless session on the launch's flags and reports
`session exit 1: Not logged in` (L1's case). The wave skill runs `doctor --probe` once per wave
session, before its first `launch-builder`, and stops with the probe's line when it fails.

### 3.8 Respec

Input: #240, #242, #245, #246, with their highs.

**A foreman spec finding reaches the owner** (#240):
- A `deviation (spec)` finding raised by `collect --spec` is owner-only, as a test-delta finding
  is. It is never sent to the judges, in either mode.
- Contested or not, it opens a point-1 decision that offers `respec` beside `upheld` and
  `overruled`. `skills/wave/references/decision_points.md` says so, beside its owner-only row.
- `<fid> respec` is a form in `FORM_RES`, so a ruling posted by hand or from the inbox parses.
- A question in the `## Q<n>` form yields the `<fid> respec` option.
- A ruling on a contest copy also settles the original finding.
- An open respec file is keyed by unit, head cycle and fid, so a foreman fid repeated in a later
  head cycle cannot collide.
- `foreman-1-1 foreman-1-1 respec` is a refusal, not a `KeyError`.
- There is one `SPEC_CLAIM`, in `decision.py`, which `collect.py` imports.

**A respec reaches every unit it touches** (#242, #245 astra-5-1):
- A change to prose under `## Units` that is outside the table's rows touches every unfiled or
  unmerged unit. This is deliberately broad: such prose is a build rule.
- An Interfaces name is the identifier before any `(`, `->` or space, so `load(path) -> dict` and
  `load` are one name. A line naming a store key (`` `state.json` key `x` ``) is keyed by the key.
  `- Produces: none` names nothing.
- Table lines are exempt from the quoted-line and range rules.
- `ingest_pr` ignores an external finding outside the respec's scope when the approval is a
  respec.
- `approve-spec --respec` passes the repository root through to `history`, so it works after the
  approving worktree is removed.

**The wave ends** (#246):
- `report`'s merge rounds leave out a unit whose respec is open (`waiting respec`).
- A batch with nothing to launch, where every remaining unit waits on an open respec, ends the
  wave with `waiting: respec R<n>`.

**The replan gate and respec files** (#245 codebase-details-5-1, #246 codebase-details-5-2 and 5-3):
- The gate checks every unit's replan mark before the body-hash refusal.
- `launch-builder` refuses a unit held by a `replan:` mark, as it refuses one held by `respec:`.
- `respec.py` refuses an unreadable respec file, or one that is not a JSON object, with its path,
  and `status.respec_lines` prints that refusal as a `respec: read failed: <path>: <reason>` line
  instead of crashing.

### 3.9 The inbox

Input: #236, #250, L21.

- **A proceed pins the head the owner saw.** The inbox shows the head sha with every proceed
  offer.
  - The posted form becomes `**Ruling:** proceed <sha7> — <reason>`. It pins that head and is
    refused when the unit's head has moved since.
  - The typed form, on a head review, is `review rule --ruling proceed --head <sha7> --owner
    --reason <text>`, with the same refusal.
  - On a head review, a proceed without a head is refused with `proceed needs the head: write
    "proceed <sha7> — <reason>"`. Spec and plan reviews keep the bare form.
  - Proceeds already recorded keep their pinned head. `skills/wave/references/rulings.md` and the
    inbox skill show the new forms.
- **The repository check.** The inbox compares each handoff's frozen `repo` with `config.repo`.
  On a mismatch, that handoff's lines are replaced by
  `repo mismatch: <handoff> was approved for <repo>`, and nothing is offered for it.
- An undo after a proceed is refused while the proceed's merge is still offered.
- The cap command in `skills/inbox/SKILL.md` carries `--runcard`.
- A capped round's contest that no panel will rule gets an inbox line.
- **The merge step** (`skills/inbox/SKILL.md` step 9) runs `gh pr ready <n> -R <repo>` first when
  the pull request is a draft. Its method and `--admin` rules are unchanged (L21).
- `report.pending_decisions` matches a decision's verdict file by its path, not by searching the
  question text, so a builder's text cannot make a decision pending.
- The #250 test-fixture rows (`tests/unit/test_inbox.py`, `tests/unit/test_u72.py`) are fixed.

### 3.10 The rest, by owning file

- **Plan and approval** (L4, L11, L44, #235):
  - `step_paths` reads only path-shaped spans: a span with a `/` or ending in a file extension.
  - `load_config` checks each `reviewers.*` panel the way CI does, so a trimmed panel fails when the
    config is written, not first in CI.
  - `approve-spec` refuses when `.superegm/config.json` has uncommitted changes it did not make.
  - The review location regex stops at whitespace (#235).
- **Post-mortem and retro** (#239, #249): the external copies' dispositions are counted, contest
  copies are not counted twice, `--not-run` rounds are not head rounds, a round of only copies
  counts as quiet, a `redesign` stop counts in Lessons, findings of unapproved respec cycles are
  kept, `**Reply <fid>:**` is a label, the test_u87 fixture and comment are fixed, and
  `next answer --answer ''` is refused.
- **Clean** (#253):
  - Before each signal, `clean` reads the process's start time (`ps -o lstart= -p <pid>`, on macOS
    and Linux) and compares it with the time it read when it listed the process. A different or
    unreadable start time skips that process and prints `kept <pid>: identity changed`. No launch
    record is needed, so a 1.2.1 launch is covered.
  - After the wait, `clean` lists again and treats a process found then as a new one.
  - `close` saves a merge it reads from GitHub.
  - `rmdir` never runs through a symlink.
  - The docs and docstrings say that one undeletable ref keeps only itself.
  - A test pins that a closed handoff still loads through its integrate card (#253's open
    question, which the check found WRONG).
- **Doctor** (#217): no `--allow` hint for a subcommand that runs commands or pushes:
  `git subtree`, `git rebase --exec`, `git submodule foreach`, `git bisect run`,
  `gh alias set --shell` and `gh extension`.
- **Judges wording** (#250 codebase-details-5-3): `decision_points.md` names the refused round and
  the refused redesign.

### 3.11 Left out

- L2 (case-insensitive decision ids): marked NOT-A-BUG; the ids print in lower case.
- L10 (a spec amendment makes every unit due again in review-plan): the rendered body carries the
  spec's sha in two places, and `gate` and `apply` check the exact reviewed bytes before filing.
  Changing the identity for review-plan alone deadlocks filing; changing it everywhere weakens the
  filing check. The owner records unchanged units as carried, as in 1.2.1.
- L12 (a rule that a spec template names the card of every write): process, not code. This design
  names the card of every write it adds.
- L20 (a general rule that the helper's tests are hermetic to the DoD environment): the one failing
  case was fixed in 1.2.1 (#181).
- L22 (reusing a round's panel on an unchanged head): it saves cost and fixes nothing broken, and
  an unchanged head does not mean unchanged review inputs. The retry of a failed `collect` (§3.4)
  covers the costly case.
- L23 (a push or a pull request opening does not restart the stall clock): the helper records
  neither locally. The 60-minute default (§3.3) covers the case seen.
- L28 (a reviewer's finding that restates an already-overruled foreman finding): nothing links the
  two fids, and anti-goal 3 forbids matching by wording. The owner rules such a contest once.
- L32 (an unexplained relaunch at 05:46Z): unsure; most likely a driver tick, which is not a bug.
- L33 (naming which unit owns a stale neighbouring file): the builder already reports it as out of
  Scope.
- L44's remainder (helper commands stop with "spec changed since the approval" while an amendment
  awaits approval): 1.2.1's respec path (1.2.1 §7.6) is how the build corrects a spec now, and it
  does not stop the wave.
- Rows the inputs file marks FIXED, NOT-A-BUG or WRONG, except the WRONG row's test (§3.10).

## 4. Tracks

### 4.1 What a track is

A track is one piece of work: its status, the track it came from, its links, and the evidence
that closes it. There are two sorts.

**Derived tracks** are read from the store each time a track command runs, and are never written:
- One per handoff, id `h:<handoff id>`. Title: the spec's H1 from the approval entry. Links:
  `handoff:<id>`, `spec:<path>`, and `issue:#<n>` for its tracking issue when `state.json` records
  one.
- One per filed unit, id `u:<handoff id>/<U>`. Title: `<U>: <unit title>`. Links: `unit:<U>`,
  `issue:#<n>`, and `pr:#<n>` once a pull request is saved. Its origin is its handoff's track.
- One per respec, id `r:<handoff id>/R<n>`. Title: `<handoff>: respec R<n>`. Its origin is its
  handoff's track.

They show what the store last recorded; a merge shows once `status` has seen it, as everything
else in SuperEGM does. They need no backfill: a 1.2.1 store's handoffs and units are tracks from
the first `track list`.

**Owned tracks** are the ones the store cannot know: a release, a fix found mid-wave, a feature,
anything else. They live in `<artifacts_dir>/tracks/tracks.json` (a `Store.LEVEL` kind `tracks`,
file name `tracks`), with ids `T<n>` counting up, never reused. The same file holds the origin
edges the owner sets on derived tracks.

```json
{"tracks": [
  {"id": "T3", "title": "1.3 release", "kind": "release", "status": "in progress",
   "origin": null, "links": ["spec:docs/specs/2026-11-24-superegm-1.3-design.md"],
   "evidence": null, "opened_at": "…", "closed_at": null,
   "history": [{"at": "…", "status": "in progress", "by": "track set"}]}
 ],
 "origins": {"h:2026-11-24-superegm-xxxxxx": "T3"}}
```

Every track, either sort, has:
- **kind**: `release`, `handoff`, `unit`, `respec`, `fix`, `feature`, `redesign` or `other`.
  Derived tracks are `handoff`, `unit` and `respec`.
- **status**: `not started`, `in progress`, `done` or `dropped`.
- **origin**: a track id or null. Origins form a tree: a track's origin cannot be itself or one of
  its descendants.
- **links**: typed strings: `handoff:<id>`, `unit:<U>`, `issue:#<n>`, `pr:#<n>`, `spec:<path>`,
  `commit:<sha>`, `review:<id>`, `url:<url>`.
- **evidence**: required for `done` and `dropped`, and absent otherwise.

Evidence is built only from what the store records. Its forms:

| Evidence | Form | From |
|---|---|---|
| A merged pull request | `pr:#<n> merged <YYYY-MM-DD>` | the saved pull request's `mergedAt` |
| A landing the owner confirmed | `landed, confirmed by the owner <YYYY-MM-DD>` | `units.<U>.landed_confirmed` |
| A stop | `stopped by <owner or judges>: <reason, or "no reason given">` | the stop ruling in `foreman/<U>.json` |
| A redesign | `redesign by <owner or judges>; brief <path>` | the ruling and `stopped.brief` |
| A closed handoff | `closed <YYYY-MM-DD>; <k> units landed, <m> not` | `closed_at` and the unit tracks |
| A unit its handoff closed without | `handoff closed <YYYY-MM-DD> without it` | the handoff's `closed_at` |
| A voided approval | `approval voided by <voided_by>` | the approval entry's `voided_by` |
| An approved respec | `commit:<sha7> approved <review id>` | the respec's approval entry |
| A respec withdrawn | `withdrawn: <the reason respec.open records>` | the respec records |
| The owner's word | `owner: <text>` | `track set` |

### 4.2 How derived tracks get their status

The first rule that matches, top to bottom, decides.

| Track | Rules |
|---|---|
| Handoff | latest approval voided: `dropped` (voided-approval evidence); `closed_at` set: `done` (closed-handoff evidence); otherwise `in progress` |
| Unit | saved pull request merged: `done` (merged-PR evidence); `landed_confirmed` set: `done` (confirmed-landing evidence); a stop or redesign recorded: `dropped` (stop or redesign evidence); its handoff closed: `dropped` (handoff-closed-without evidence); a launch recorded: `in progress`; otherwise `not started` |
| Respec | approval recorded: `done` (approved-respec evidence); left out by `respec.open` (its unit stopped, its handoff superseded): `dropped` (withdrawn evidence); otherwise `in progress` |

A derived track's status cannot be set by hand: `track set` on one is refused with
`<id> is derived from the store`. The owner can set its origin with `track origin`.

### 4.3 The `track` subcommand

`superegm track` is one new subcommand, in a new module `track.py` (the helper's tests require a
module's name to be its command's). A `track` card's artifact is the literal `store`, which
`require_runcard` accepts for the `track` and `sweep` skills only. Every form that writes takes
`--runcard`, and typed without it opens and closes its own `track` card, as `approve-spec --void`
does.
- `track add --kind <kind> --title <text> [--origin <id>] [--link <link>]…` adds an owned track,
  `not started`.
- `track set T<n> --status <status> [--evidence <text>]` changes an owned track's status. `done`
  and `dropped` require evidence; typed evidence is stored as `owner: <text>`.
- `track link T<n> <link>` adds a link to an owned track.
- `track origin <id> <origin id>` sets the origin of any track, refused if it would make a cycle.
- `track show <id>` prints the track, its history, its origin chain and its children.
- `track list [--status …] [--kind …] [--open]` prints one line per track, derived and owned.
- `track find <text>` matches ids, titles, links and evidence: `#301`, `U104` and `pr:#320` all
  work. It prints one line per match, status first.

### 4.4 Who reads tracks

- **The owner's elephant session.** `using-superegm` gains one line: before starting work on a bug,
  a TODO, an issue or a plan item, run `superegm track find` on it, and if a track for it is
  `done` or `dropped`, say so and show the evidence before doing anything. The brainstorming
  skill does the same for a new brainstorm's topic.
- **The inbox.** The inbox's `redesign` row for a stopped unit (`inbox.py:513-516`) stays until the
  unit's track has a child, that is until the owner has linked the redesign's work with
  `track origin <new track> u:<handoff>/<U>`. The row's text names that command. No other inbox row
  changes: kill, conflict, decision and merge rows are shown as today, whatever a track says.
- **The sweep** (§5) uses a track's status as evidence.
- Builders, the foreman, reviewers and judges do not read tracks.

## 5. The sweep

### 5.1 What it looks for

`/superegm:sweep` is typed only, like every skill with external effects; it writes into the
store. The skill opens a `sweep` card (artifact `store`, §4.3), and both helper calls below run
under it. `superegm sweep candidates [--max <n>] --runcard <card>` writes
`<artifacts_dir>/sweep/<sweep id>.json` (`<sweep id>` is `<YYYYMMDD>-<n>`) and prints the id and
the number of candidates. Its sources:

1. **TODOs**: every `TODO`, `FIXME` and `XXX` line in a tracked file (`git grep -n`), leaving out
   `docs/specs/` and `tests/`. A TODO that names an issue (`#<n>`, a GitHub issue URL) or a unit
   (`U<n>`) is a candidate with that issue's state and the matching track's status. A TODO with no
   reference is a candidate only when the line's own blame date is more than 90 days old.
2. **Specs**: a file under `docs/specs/` is a candidate when it has no approval entry and was last
   changed more than 90 days ago (an abandoned draft), or when its latest approval is voided.
   Whether a spec's cited paths and symbols still exist is `drift-report`'s job, not the sweep's.
3. **Rules files**: every tracked file named `CLAUDE.md`, `AGENTS.md` or `GEMINI.md` at any depth,
   `.claude/**/*.md`, and the files of `instructions`. A line is a candidate when a backticked span
   in it holds a `/`, holds none of `<`, `>`, `*` and `{`, and names no tracked file or directory,
   resolved from the repository root. Commands, bare file names and other words are not checked.

Candidates are ordered oldest first, by blame date, and cut to `--max` (default 60). The cut and
the total are printed. Each candidate is `{"id": "c<n>", "source": "todo|spec|rules", "file",
"line", "text", "evidence": {…}}`. The evidence is what the checker cannot gather itself, because
it can read but cannot run git or `gh`: the line's blame date and commit, `git log -n 5 --format=%h
%ad %s` of the file, the state of each named issue or pull request, each matching track's id and
status, and whether each path-shaped span exists. The helper judges nothing.

### 5.2 Who checks

- The skill tells the owner how many sweeper dispatches the candidates need, one per batch of up to
  20, and asks once before dispatching.
- It dispatches a new read-only adapter, `superegm:sweeper` (tools `[Read, Grep, Glob]`,
  `omitClaudeMd: true`), once per batch, on `config.reviewers.model` at `config.reviewers.effort`,
  as a review goldfish is.
- It is a goldfish: it sees only its batch, the sweep file and the repository at `HEAD`. It ends its
  reply with a `saw:` line.
- It answers one line per candidate: `<candidate id> | stale|still true|unsure | <evidence>`.
  `stale` requires evidence cited from the candidate's evidence or the code.

### 5.3 What the owner gets

- After each batch, the skill runs `superegm sweep record --sweep <sweep id> --answers <file>
  --isolation <clean|exposed:…> --runcard <card>`. It checks that each answer names a candidate of
  the sweep that has no answer yet and follows the grammar, stores the answers and that batch's
  isolation in the sweep file, and rewrites `<artifacts_dir>/sweep/<sweep id>.md` from everything
  recorded so far. The helper stays the store's only writer.
- The skill shows the owner the `stale` rows grouped by file, each with its evidence and a
  suggested change (delete the TODO, update the line, mark the spec abandoned), then the `unsure`
  rows. `still true` rows are counted, not listed.
- The sweep changes nothing (anti-goal 5). If the owner picks rows, the skill offers to make those
  edits as an ordinary small change on a new branch, for the owner to review and merge.
- `drift-report` and `clean` are unchanged, and the README's "three hygiene tools" table stands.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| A lock is held by a crashed process | `flock` is released by the kernel when the process exits; a lock is held only inside one save (§3.1) |
| A save refuses with `concurrent change` mid-wave | The command writes nothing; the session that ran it runs it again, and its refusals are checked again on fresh data |
| Round files, `review.json` or `launches/<U>.json` lose a concurrent write | Not seen in 1.2.1; their writers are mostly one unit's foreman flow, in sequence. Left for a later release (§2 non-goals) |
| A builder pushes to another ref | The typed route is gone (§3.7), but a script run through `pytest` or a DoD command can still push with the launch's credentials. Branch protection on the base branch is the guard, as in 1.2.1 |
| Organisation-managed hooks run inside builders | The owner cannot remove them. `doctor` and each launch record name them (§3.7); the owner runs builds knowing which hooks run |
| A comment is spoofed or edited | Only the builder's identity and `config.owners` logins reach the prompt, per form; an edited comment or review is left out (§3.7) |
| `CI green on the head` stands in for the full suite | CI runs on Ubuntu with Python 3.11, not the owner's macOS, so a macOS-only failure passes the gate. Accepted: CI was already the 1.2.1 gate's CI check |
| A derived track is stale | It shows what the store last recorded; `status` updates the store on every wave pass. Nothing acts on a track's status except the inbox's redesign row, which waits for an owner link |
| The sweep calls something stale wrongly, or costs too much | A fresh read-only goldfish must cite evidence; the owner decides; the sweep edits nothing; `--max` caps the candidates and the owner sees the dispatch count first |
| The mid-wave reinstall breaks a running handoff | It happens between batches, with no builder or foreman running; §6 requires 1.3 to open a 1.2.1 store unchanged, and U98's tests include one |
| Parallel §3 units conflict on shared files | `review.py`, `decision.py`, `collect.py` and `launch_builder.py` are each in three to six units' Scope. Each conflict costs a merge-round relaunch, as in 1.2.1; the plan orders merges by shared file |

## 11. Alternatives Considered

The team brainstorm was not asked for: `team: off`, with no subagents. The elephant's two
fresh-subagent checks of the deferred work (the inputs file) are evidence, not approaches.

- **Where tracks live.** The store, a data branch (`superegm/tracks`), or GitHub issues. The owner
  chose the store. A data branch would be durable and shared, but needs push, conflict and offline
  handling and splits state between two places. GitHub issues would make every track an issue,
  against the README's "including work that never had an issue".
- **Track records written by every workflow step.** The first draft stored handoff and unit tracks
  as rows, written by six subcommands, with a backfill. Rejected after the spec review's first
  round: those rows would copy facts the store already holds and could drift from them. Derived
  tracks (§4.1) read the facts in place.
- **How to stop lost writes.** Considered:
  - A lock around each caller's whole read-change-write, with every caller converted and the old
    save functions removed (the second draft). Rejected after round 2: about a dozen modules call
    `save_state`, so the conversion spread across units and the removal broke modules outside them.
  - Optimistic writes with a version number and retry in every caller, `sqlite3` transactions, or
    one writer process. Each changes every caller or adds a migration or a daemon.
  - A three-way merge inside the save functions (chosen): no caller changes, a conflict refuses
    instead of overwriting, and the `flock` idiom is already in the helper (`driver.py`).
- **`foreman.ci_covers`, a config key listing commands CI stands in for.** Rejected in round 1:
  1.2.1's `load_config` refuses an unknown foreman key, so this repository could not set it before
  the reinstall, and the plan grammar already has `CI green on the head`. A `scan` refusal of a
  full-suite `Run` item was rejected in round 2: matching command text misses variants and refuses
  fast suites in other repositories.
- **Raising the foreman's 9-minute cap to 15** (the mid-wave hotfix). Rejected: above the Bash
  tool's 10-minute limit `collect` would have to run in the background, and a subagent's background
  command dies when the subagent returns.
- **Loosening the builder allow-list** (L15, L51 to L53). Rejected by anti-goal 1.
- **A second mid-wave reinstall for the tracks and sweep units.** Rejected in round 2: only the
  docs unit and the old handoffs' closing would use it, and both can wait for the release.
- **Ship the fixes as 1.2.2 first.** Rejected by the owner: one release, with §3 first.
