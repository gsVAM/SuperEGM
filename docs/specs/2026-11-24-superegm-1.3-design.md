## 1. Intent

1.3 is about **not doing the same work twice, and not being misled by work that is already
done.** The owner's README puts it this way: an agent that reads a stale TODO, an old plan, or an
out-of-date line in `CLAUDE.md` treats it as an instruction.

The 1.2.1 build showed the same problem from inside SuperEGM:
- Handoffs whose work had landed still showed as open. Six handoffs in the store have no
  `closed_at`, and tracking issues #21, #35, #117 and #193 are open for work that merged long ago.
- Units lost their `launched` mark because one command overwrote another's write (§3.1).
- Settled findings came back as new highs round after round (§3.5).
- Eleven units hit their round cap and merged with findings left open. Those findings live only in
  retro issues, and 55 of 59 are still true at 8b7032e.

So 1.3 has three parts, built in this order:

1. **Fix what the 1.3 wave itself runs on** (§3). The store, GitHub calls, the foreman's gate,
   rulings, respec and the inbox all carry known defects, and the 1.3 wave would hit them again.
   They land first.
2. **Tracks** (§4): a record, per piece of work, of whether it is finished, where it came from and
   what shows it.
3. **The sweep** (§5): a skill that finds stale TODOs, plans, specs and rules-file lines. A
   separate fresh agent checks each one against the code and git history before anything is
   called stale.

## 2. Goals, non-goals, anti-goals

Goals:
1. No write to `state.json`, a unit's `foreman/<U>.json` or `tracks.json` is lost to a concurrent
   helper command (§3.1). These are the store files that several commands read, change and write
   back; a round's files are written once, by one command.
2. A transient GitHub error never ends a helper command with a traceback (§3.2).
3. A unit whose Definition of done runs the full test suite can pass the foreman's gate (§3.3).
4. Every open or partly fixed row of the inputs file is fixed, or is named in §2's non-goals or
   §3.11 with a reason.
5. Every piece of work SuperEGM runs (a handoff, a unit, a respec, a fix found mid-wave) has a
   track whose status is true. A finished one carries evidence a reader can check.
6. `/superegm:sweep` reports stale material with evidence and changes nothing on its own.
7. The 1.3 README says what 1.3 ships, and nothing it does not.

Non-goals:
- Sharing tracks across machines or people. Tracks stay in the store, by the owner's choice. A
  later release may mirror them to a data branch; nothing in this design prepares for that.
- Putting tracks into a builder's prompt. The agent that decides what work to start is the owner's
  elephant session, and that is the session tracks serve (§4.4). A builder works one unit's Scope
  and does not choose work.
- Removing stale material automatically. The sweep reports, and the owner decides (§5).
- Lesson 16 (an "already passing" Step fails `tdd-order`). The elephant's call is to keep the
  deviation path: a Step whose test passes before any change is a deviation the builder posts, as
  the orders already say. §3.7 makes the orders say it where builders look.
- Lesson 33 (naming which unit owns a stale neighbouring file). Low value; the builder already
  reports it as out of Scope.
- Lesson 32 (an unexplained relaunch at 05:46Z). The evidence is in the store's journal. If it was
  a driver tick, §3.1's lock does not change it and nothing is wrong. Left unsure.
- Lesson 20's general rule that the helper's tests are hermetic to the DoD environment. The one
  failing case was fixed in 1.2.1 (#181).

Anti-goals:
1. **No fix widens what an unattended builder may run.** Lessons 15, 51, 52 and 53 asked for a
   looser allow-list. §3.7 instead tightens the push rule and documents the commands that exist.
2. **No text a non-owner writes reaches a builder as an instruction.** The owner's note channel
   (§3.7) reads only comments by a login in `config.owners`.
3. **No contest is dropped by matching its wording.** §3.5 drops a contest only when its fid, or
   the fid it derives from, is settled.
4. **No track is marked done without evidence**, and the helper never invents evidence: a merged
   pull request, an approval commit, a closed issue, or a sentence the owner typed (§4.1).
5. **The sweep never edits, deletes or commits anything** (§5.3).

## 3. Fixes the 1.3 wave runs on

Each subsection names its input rows: `L<n>` is Part A's lesson n, `#<n> <fid>` a Part B finding.
Every open or partly fixed row not named in a subsection is still in scope for the unit that owns
its file. §3.11 lists the rows this design leaves out.

### 3.1 The store: one writer at a time

**The defect.** `status --wait` (`status.py:178-194`) loads `state.json`, waits up to 30 minutes,
then saves the copy it loaded with `save_state`. `save_state` replaces the whole file
(`__init__.py:1791`). Any launch mark, ruling or settlement written meanwhile is lost. The comment
at `status.py:188` says the opposite. This explains L48, L49 and L56. Other read-modify-write
writers (`launch`, `record-launch`, `decision rule`) can lose writes to each other the same way.

**The fix.**
- A handoff's `state.json` is changed only through one function that takes an exclusive lock,
  reads the file fresh, applies the caller's change, writes it atomically and releases the lock.
  The lock is `fcntl.flock` on a lock file beside `state.json` in the handoff's directory.
- `status --wait` changes only `state["status"]`, through that function, after its wait.
- Every subcommand that writes `state.json` goes through it. A subcommand that must read, decide
  and write in one step does all three under the lock.
- A unit's `foreman/<U>.json` (`save_foreman`'s callers, the file of L49) and the store-level
  `tracks.json` (§4.1) use the same function, each with its own lock file.
- The lock is held only for the read-change-write, never across a GitHub call or a wait.

**Acceptance.**
- Two processes, one in `status --wait` and one writing a launch mark during the wait: both writes
  survive.
- Sixty concurrent changes to one key, from separate processes, all land.

### 3.2 GitHub calls

Input: L5, L41.
- `gh_json` retries an HTTP 502, 503 or 504, or a connection reset, up to three times with backoff
  (1, 4 and 16 seconds). Rate limits keep their own retry (`gh_retry`). A 4xx is never retried.
- A `GhError` that escapes a subcommand prints one line, `gh: <the error>`, and exits non-zero,
  the same way `HandoffError` does. It never prints a traceback.
- `discover_pr` stops listing up to 1,000 pull requests on every status pass. It looks up the
  unit's branch with `gh pr list --head <branch>` and falls back to the wider list only when that
  finds nothing.

### 3.3 The foreman's gate and its time limits

Input: L3, L14, L17, L18, #242 foreman-5-1 (high).

The full test suite takes about 11 minutes. One `collect` call is capped at 9 minutes, because the
foreman runs `collect` in the foreground under a Bash tool limit of 10 minutes. So a DoD item that
runs the whole suite can never pass. Raising the cap does not work, because a cap above 10 minutes
forces the call into the background (L14, L18).

The fix:
- **CI stands in for the full suite.** A new config key, `foreman.ci_covers`, lists the exact DoD
  commands the repository's CI runs on every head. Its default is `[]`, which changes nothing for
  any repository. A DoD item whose command equals an entry is not re-run by `collect`. It is
  satisfied when every check on that exact head sha is green, the same checks the existing
  "CI green on the head" item reads. It is recorded as `dod-<n>: ci green at <sha7>`. A red or
  missing check is `dod-<n>: ci not green`, a high, as a red re-run is today.
- This repository's `.superegm/config.json` sets `foreman.ci_covers` to `["pytest tests/unit -q",
  "python -m pytest tests/unit -q"]`, the command `.github/workflows/tests.yml` runs. The owner of
  another repository opts in only when their CI runs the same command.
- Every other DoD item is re-run as now, under the 9-minute bound.
- `foreman.run_timeout_minutes` keeps its bound of at most 9.
- `builder.stall_minutes` defaults to 60 (L3).
- The foreman brief says `collect` runs in the foreground and never with `run_in_background` (L14).

### 3.4 Recovering a round

Input: L19, L22, L43, L55.
- `review record --sha256` refuses a short value: it must be the full 64-hex sha256 for a spec or
  plan, or the full 40-hex commit sha for a pull-request head. The `prepared:` line prints the
  full value it expects (L43, L55).
- The foreman brief says that a `collect` that fails after the panel ran is run again on the same
  prepared round, which stays `prepared` until `collect` succeeds. `--not-run` is only for a round
  whose panel did not run (L19).
- `foreman dispatch` on a head whose sha equals the last posted round's head, after a ruling and
  with no new commit, offers to reuse that round's panel findings instead of dispatching the panel
  again. Only the foreman's own checks are re-run (L22).

### 3.5 Settled findings stay settled

Input: L24, L25, L39. L28 is left out (§3.11).
- A builder's contest of a fid is dropped by `collect` when that fid, or the fid it was derived
  from, is already settled by an owner ruling or a judges' ruling. Examples: a `foreman-*` finding
  derived from `dod-<n>` that the owner ruled `allowed`, or a panel finding whose foreman copy was
  overruled. The match is by fid and derivation, never by wording (anti-goal 3).
- An owner's `test-delta <file> allowed` also widens Scope for that file. The same file does not
  come back as a scope high (L25).
- A test-delta settlement is carried across rounds by file, kind and the test's name, not by base
  commit and line. A merge of main into the branch no longer re-raises it. A judges' overrule
  carries the same way (L39).

### 3.6 Rulings

Input: L34, L42, L49, L2.
- A `decision rule` refusal that is missing a fid says so: `missing <fid>: write "<fid> finding
  overruled"`.
- Decision ids are matched without regard to case (`Q1` and `q1`).
- `decision withdraw --decision <id> --reason <text>` closes an owner's mistaken pending decision.
  It is journaled and refused on a decision that already has a ruling (L49).
- A point-1 `decision rule` on a finding settles that finding itself. The separate
  `review settle --owner --posted` step is no longer needed and still works (L42).

### 3.7 Builder launch, orders and the owner's note

Input: L1, L9, L13, L15, L51, L52, L53, L54.

**The push.** The allow-list entry `Bash(git push origin <branch>:*)` is a prefix, so it also
matches `git push origin <branch>:main`. Only branch protection stops that push. A prefix entry
cannot exclude a refspec (`docs/claude.md`).
- In the elephant's call, `launch-builder` writes a `superegm-push` script into the launch's
  `_bin` directory, next to the `gh` shim. The script ignores its arguments and runs
  `git push -u origin HEAD:refs/heads/<branch>` with the branch fixed at launch.
- The allow-list carries that script's absolute path in place of every `git push` entry, and the
  orders say `{{push}}`.
- A builder therefore cannot push to any other ref, whatever it types. Adding `-q` and `-u`
  variants (the mid-wave hotfix) is not carried into the source.

**The orders** (`skills/wave/references/builder_orders.md`) gain one short section:
- The commands the allow-list permits, as `launch-builder` writes them.
- The rule: one command per Bash call, with no pipes, `;`, `&&` or heredocs.
- Comments and PR bodies are written to a file with Write and posted with one `gh … --body-file`
  call (L51 to L53).
- The check for an existing PR is `gh pr view <branch>` (L54).
- Every file the builder changes, tests included, gets its `<what>` in the file's "Modified by
  SuperEGM" provenance header (L9).
- A Step whose test passes before any change is posted as a deviation (non-goals, lesson 16).

**The owner's note.**
- An issue comment whose first line is `**Note:** <text>`, by a login in `config.owners`, is
  carried into every later launch prompt of that unit under `# Owner notes`, oldest first.
- A `**Note:**` by anyone else is ignored and journaled as `note ignored: <login> is not an owner`
  (anti-goal 2). This closes L13.

**Managed settings in the profile.** The builder profile's `remote-settings.json`, the
organisation's managed settings that Claude Code syncs, can carry `hooks` and `enabledPlugins`. On
this machine it does. `doctor` checks only `settings.json`, so it misses them. `doctor` gains an
informational `managed:` line naming each managed hook event and plugin in the profile. It is
informational because the owner cannot remove managed settings. `launch-builder` records the same
names in the launch's `_plugins.json`, as it records the plugins it loads.

**The profile's login.** `launch-builder` refuses a builder profile with no saved Claude Code
login. The same check is a `profile:` line in `doctor` (L1). How to detect the login on disk is
left to the builder, checked on this machine.

### 3.8 Respec

Input: #240 (two highs), #242 (two highs), #245, #246 (one high), and their mediums and lows.

**A foreman spec finding reaches the owner** (#240):
- A `deviation (spec)` finding raised by `collect --spec` is owner-only, as a test-delta finding
  is. It is never sent to the judges, in either mode.
- Contested or not, it opens a point-1 decision that offers `respec`, beside `upheld` and
  `overruled`.
- `<fid> respec` is a form in `FORM_RES`, so a hand-posted or inbox-posted ruling parses.
- A question in the `## Q<n>` form yields the `<fid> respec` option.
- A ruling on a contest copy also settles the original finding.
- Open respec files are keyed so that a foreman fid repeated in a later head cycle cannot collide
  (#240 codebase-details-5-6).
- `foreman-1-1 foreman-1-1 respec` is a refusal, not a `KeyError`.
- There is one `SPEC_CLAIM`, imported from `decision.py`.

**A respec reaches every unit it touches** (#242):
- A change to prose under `## Units` that is outside the table's rows touches every unfiled or
  unmerged unit. This is deliberately broad: such prose is a build rule.
- An Interfaces name is the identifier before any `(`, `->` or space, so `load(path) -> dict` and
  `load` are one name.
- A line naming a store key (`` `state.json` key `x` ``) is keyed by the key, not the file name.
- `- Produces: none` names nothing.
- Table lines are exempt from the quoted-line and range rules.
- `ingest_pr` ignores an external finding outside the respec's scope when the approval is a respec.
- `approve-spec --respec` passes the repository root through to `history`, so it works after the
  approving worktree is removed (#245 astra-5-1).

**The wave ends** (#246):
- `report`'s merge rounds leave out a unit whose respec is open (`waiting respec`).
- A batch with nothing to launch, where every remaining unit waits on an open respec, ends the wave
  with `waiting: respec R<n>`. It does not continue.

**The replan gate** (#245 codebase-details-5-1, #246 codebase-details-5-2 and 5-3):
- The gate checks every unit's replan mark before the body-hash refusal, so one unit's refusal
  cannot hide another unit's mark.
- `launch-builder` refuses a unit held by a `replan:` mark, as it refuses one held by `respec:`.
- An unreadable respec file is refused with its path, and so is one that is not a JSON object.

### 3.9 The inbox

Input: #236 (two highs and three others), #250 (open rows), L21.
- **A proceed pins the head the owner saw.** The inbox shows the head sha with every proceed
  offer. A posted `**Ruling:** proceed <sha7> — <reason>` pins that head, and is refused when the
  unit's head has moved. A typed proceed pins the head the inbox printed.
- **The inbox checks each handoff's frozen `repo` against `config.repo`.** On a mismatch, that
  handoff's lines are replaced by `repo mismatch: <handoff> was approved for <repo>`, and nothing
  is offered for it.
- An undo after a proceed is refused while the proceed's merge is still offered.
- The cap command in `skills/inbox/SKILL.md` carries `--runcard`.
- A capped round's contest that no panel will rule gets an inbox line (#250).
- **The merge runs `gh pr ready <n>` first** when the pull request is a draft, then
  `gh pr merge --squash --admin --match-head-commit <sha>` (L21).
- `report.pending_decisions` matches a decision's verdict file by path, not by searching the
  question text, so builder text cannot make a decision pending (#250 codebase-details-5-5).

- **Foreman brief and output** (L7, L8): the brief tells the foreman to pass `model` and `effort`
  on every Agent call. `collect` prints each finding's line, not just a count.
- **Plan and scan** (L4, L10, L11, L44, #235):

- **Post-mortem and retro** (#239, #249): every open row. The external copies' dispositions are

## 4. Tracks

### 4.1 What a track is

A track is one piece of work. The store holds them all in one file, `<artifacts_dir>/tracks.json`,
at the store level: a new `Store.LEVEL` kind `tracks`, written only through §3.1's locked update.

```json
{"tracks": [
  {"id": "T12",
   "title": "U104: a foreman spec finding reaches the owner",
   "kind": "unit",
   "status": "done",
   "origin": "T7",
   "links": ["handoff:2026-11-24-superegm-xxxxxx", "unit:U104", "issue:#301", "pr:#320"],
   "evidence": "pr:#320 merged 2026-12-02 at 3f2a91c",
   "opened_at": "2026-11-25T10:00:00Z",
   "closed_at": "2026-12-02T09:14:00Z",
   "history": [{"at": "…", "status": "in progress", "by": "file"},
               {"at": "…", "status": "done", "by": "close"}]}
]}
```

- **id**: `T<n>`, counting up, never reused.
- **kind**: one of `release`, `handoff`, `unit`, `amendment`, `fix`, `feature`, `redesign`,
  `other`. A spun-off wave is a `handoff` whose origin is the handoff it came from.
- **status**: `not started`, `in progress`, `done` or `dropped`.
- **origin**: the track it came from, or null. Origins form a tree. A track's origin cannot be
  itself or one of its descendants.
- **links**: typed strings: `handoff:<id>`, `unit:<U>`, `issue:#<n>`, `pr:#<n>`, `spec:<path>`,
  `commit:<sha>`, `review:<id>`, `url:<url>`.
- **evidence**: required when status is `done` or `dropped`, refused otherwise. It is a merged PR
  (`pr:#<n> merged <date> at <sha7>`), an approval commit, a closed issue, or the owner's typed
  sentence, prefixed `owner:`. For `dropped`, it says why, and names the superseding track if
  there is one.
- **history**: every status change, with time and the subcommand that made it (`by`).

### 4.2 The workflow writes tracks

Tracks build themselves as the workflow runs. Each write below happens in a subcommand that
already writes the store, under its existing run card, with `tracks` added to its `WRITES`.

| Event | Subcommand | Track change |
|---|---|---|
| A spec's first approval opens a handoff | `approve-spec` | New `handoff` track, `in progress`, links `handoff:`, `spec:`; origin is the track named by `--track` if given, else null |
| A respec is approved | `approve-spec --respec` | New `amendment` track, origin the handoff's track, `done`, evidence the approval commit |
| A unit's issue is filed | `apply` | New `unit` track, `not started`, origin the handoff's track, links `unit:`, `issue:` |
| A unit's builder first launches | `launch-builder` | The unit's track `in progress` |
| A unit's PR is merged | `status` (when it sees the merge) and `close` | The unit's track `done`, evidence the merged PR |
| A unit is stopped and not redesigned | `decision rule` (stop) | The unit's track `dropped`, evidence the ruling's reason |
| A unit is stopped for redesign | `decision rule` (redesign) | The unit's track `dropped` with evidence `redesign: <brief path>` |
| A handoff closes | `close` | The handoff's track `done` when every unit track is `done` or `dropped`, evidence the close commit; otherwise it stays `in progress` and `close` prints the open ones |

No other subcommand writes `tracks.json`. Nothing records which later units redesign a stopped
one, so their origin is set by hand: when the redesign's units are filed, the elephant offers
`track origin T<new> T<stopped>` for each, and the owner says yes or no.

### 4.3 The owner writes tracks

`superegm track` is one new subcommand. Every form that writes opens and closes its own `track`
card when typed without `--runcard`, as `approve-spec --void` does.
- `track add --kind <kind> --title <text> [--origin T<n>] [--link <link>]…` adds a track,
  `not started`.
- `track set T<n> --status <status> [--evidence <text>]` changes status. `done` and `dropped`
  require evidence. Typed evidence is stored as `owner: <text>`.
- `track link T<n> <link>` adds a link. `track origin T<n> T<m>` sets the origin, refused if it
  would make a cycle.
- `track show T<n>` prints the track, its history, its origin chain and its children.
- `track list [--status …] [--kind …] [--open]` prints one line per track.
- `track find <text>` matches title, link and evidence. `#301`, `U104` and `pr:#320` all work.
  It prints one line per match, status first.

A fix found mid-wave becomes `track add --kind fix --origin T<unit>`. The elephant offers that when
the owner rules a finding out of a unit's scope, or when a retro issue is filed.

### 4.4 Who reads tracks

- **The owner's elephant session**, before starting work:
  - `using-superegm`'s rules gain one line. Before starting work on a bug, a TODO, an issue or a
    plan item, run `superegm track find` on it. If a track for it is `done` or `dropped`, say so
    and show the evidence before doing anything.
  - The brainstorming skill does the same for the topic of a new brainstorm.
- **The inbox.** `inbox` drops a stale row whose handoff or unit track is `done` or `dropped`
  (the U80/U81 `redesign` rows that motivated tracks). With `--tracks` it lists open tracks
  oldest first.
- **The sweep** (§5) uses a track's status as evidence.
- Builders, the foreman, reviewers and judges do not read tracks (non-goals).

### 4.5 Backfill

`track backfill` is typed once per store, and is idempotent. It reads `handoffs/*.json`, each
handoff's `state.json`, and GitHub state for the issue and PR numbers recorded there. It writes:
- A `handoff` track per handoff.
- A `unit` track per filed unit. A merged PR gives `done` with evidence. A stopped unit gives
  `dropped` with evidence from its stop ruling. Everything else is `in progress` or `not started`.
- No `release` tracks. The owner adds those by hand.

It prints what it wrote. It never closes a handoff or an issue. Its output tells the owner which
handoffs have every unit done or dropped and are not closed. In this repository that is expected to
include the handoffs behind tracking issues #21, #35, #117 and #193. Closing them is the owner's
call, through the existing `close` (§8).

## 5. The sweep

### 5.1 What it looks for

`/superegm:sweep` is typed only, like every skill with external effects. It writes a report into
the store. Its candidates come from one helper subcommand, `superegm sweep candidates`, which reads
the repository and GitHub and writes `sweep/<date>-<n>/candidates.json`:

1. **TODOs**: every `TODO`, `FIXME` and `XXX` in a tracked file (`git grep`, skipping `docs/specs/`
   and test fixtures). A TODO that names an issue (`#n`, a GitHub URL) or a unit (`U<n>`) gets that
   issue's state and its track's status. A TODO with no reference is a candidate only if the code
   it sits in last changed more than 90 days ago.
2. **Specs and plans**: every file under `docs/specs/`, plus any path named in
   `instructions`. For each: its approval, whether a later spec supersedes it, its handoff's track
   status, and every `path:line` and backticked path it cites that no longer exists at `HEAD`.
3. **Rules files**: `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.claude/**/*.md`, and the files of
   `instructions`. Each line that names a path, a command or a symbol is checked for existence at
   `HEAD` (`git ls-files`, `git grep -w`). A line whose name is gone is a candidate.

For each candidate the helper attaches its evidence, because the checker can read but cannot run
git. The evidence is: the `git log -n 5` of the cited path or symbol, the blame date of the line,
issue and PR states, track status, and whether each cited path exists. The helper judges nothing.

### 5.2 Who checks

- The skill dispatches a new read-only adapter, `superegm:sweeper` (tools `[Read, Grep, Glob]`,
  `omitClaudeMd: true`), one dispatch per batch of up to 20 candidates.
- It is a goldfish. It never sees the skill's conversation, only the candidates file and the
  repository at `HEAD`.
- For each candidate it answers one of:
  - `stale`, with the evidence that convinces it;
  - `still true`, with what shows it holds;
  - `unsure`.
- Nothing is called stale unless the sweeper says `stale` and cites evidence from the attached
  evidence or the code. This is the README's "the agent that found a candidate is not the agent
  that convicts it".

### 5.3 What the owner gets

- The skill passes the sweeper's answers to `superegm sweep record --sweep <date>-<n>`, which
  checks each answer names a candidate and writes `sweep/<date>-<n>/report.md`. The helper stays the
  store's only writer (§6). The skill then shows the owner the `stale` rows, grouped by
  file, each with its evidence and a suggested change (delete the TODO, update the line, mark the
  spec superseded).
- `unsure` rows come after them. `still true` rows are counted, not listed.
- The sweep changes nothing (anti-goal 5). If the owner picks rows, the skill offers to make those
  edits as an ordinary small change on a new branch, for the owner to review and merge. That is a
  normal session edit, not part of the sweep.
- `drift-report` (design docs against code) and `clean` (wave leftovers) are unchanged. The
  README's "three hygiene tools" table stands.

## 6. Constraints

- Python 3.12 standard library only, as the helper is today. No new dependency.
- Every new store write is declared in the subcommand's `WRITES`. `tracks` and `sweep` are new
  kinds: `tracks` at the store level, `sweep` at the store level.
- A 1.2.1 store opens under 1.3 with no migration step. An absent `tracks.json` reads as no tracks,
  and `track backfill` is how an owner fills it.
- A handoff approved under 1.2.1 keeps its frozen cap and mode.
- The helper's existing refusals keep their wording, except where §3 changes them.
- The helper is the only writer of the store (1.2 design), and that still holds.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| The lock deadlocks or a crashed process holds it | `flock` is released by the kernel when the process exits; the lock is never held across a wait or a GitHub call (§3.1) |
| CI stands in for a DoD item the builder could have weakened | The CI workflow is outside the builder's Scope, and the foreman already flags any change to `.github/` as a scope high; the CI check is read on the exact head sha |
| The push script is bypassed | The allow-list has no `git push` entry left; a builder typing `git push` is refused by Claude Code |
| An owner note is spoofed | Only `config.owners` logins count, checked on the comment's author, the same check rulings use |
| Tracks drift from GitHub | Every workflow write in §4.2 happens where the helper already learns the fact; `track backfill` re-derives from the store and GitHub and is safe to re-run |
| The sweep calls something stale wrongly | A fresh read-only goldfish must cite evidence; the owner decides; nothing is edited by the sweep |
| 1.3 is large, 21 units | §3's fifteen units have no code dependencies on each other and run in parallel; tracks and the sweep follow on the reinstalled build (§8) |
| The mid-wave reinstall breaks a running handoff | The reinstall happens between batches, with no builder or foreman running; §6 requires 1.3 to open a 1.2.1 store unchanged, and U98's tests include a store written by 1.2.1 |

## 11. Alternatives Considered

The team brainstorm was not asked for: `team: off`, with no subagents. The elephant's two
fresh-subagent checks of the deferred work (the inputs file) are evidence, not approaches.

- **Where tracks live.** The options were the store, a data branch (`superegm/tracks`) in the
  repository, and GitHub issues. The owner chose the store. A data branch would be durable and
  shared but needs push, conflict and offline handling, and would split state between two places.
  GitHub issues would make every track an issue, against the README's "including work that never
  had an issue".
- **Ship the fixes as 1.2.2 first, then 1.3.** Rejected by the owner: one release. §3's units still
  land first in the chain, so the 1.3 wave benefits from them.
- **Raise the foreman's 9-minute cap to 15** (the mid-wave hotfix). Rejected: above 10 minutes
  `collect` must run in the background, which L14 and §3.1 show is unsafe. CI standing in for the
  full suite (§3.3) removes the need.
- **Loosen the builder allow-list** (L15, L51 to L53). Rejected by anti-goal 1. Documenting the
  rule, and a push script that can only push one ref, fix the friction without widening anything.
- **Tracks in builder prompts.** Rejected for 1.3 (non-goals): a builder does not choose work.
- **A sweep that opens its own cleanup PR.** Rejected: the owner decides each row (§5.3).
