# inbox

In Claude Code or Cowork, read `${CLAUDE_PLUGIN_ROOT}/docs/claude.md` first.

    python3 '<HELPER>' inbox [--all] [--json] [--handoff <id>]
    python3 '<HELPER>' inbox withdrawn --pr <n> --reason <text> [--runcard <card>] [--handoff <id>]

`<HELPER>` is `${CLAUDE_PLUGIN_ROOT}/skills/plan/scripts/superegm.py`. Run `superegm inbox` and show its lines to the owner as printed; then, for the items the owner answers here, run `superegm inbox --json` (with `--all` when the lines came from `--all`) and work from its objects. Each object names its `handoff`; run every command for an item from its store's root (under `--all`, the `root` of the `~/.superegm/registry.json` entry whose `artifacts_dir` is the item's store's; else the current repository), where `--handoff <id>` resolves.

No skill asks the owner to post a comment or to paste a command: the inbox asks in words and does the rest. A comment the owner posts on GitHub by hand still counts; the inbox is the way, not the only way.

## What it lists

Listing is read-only: no run card, no store write, no GitHub call (`superegm inbox withdrawn`, the merge step's withdraw, is the exception: it journals one line and opens and closes its own inbox card); `superegm inbox` typed alone prints and never notifies, and any session may run it. It reads the current repository's store, every open handoff of its `handoffs/` index unless `--handoff` names one; `--all` reads every store the registry lists (`registry: none`, and the one store, while nothing is registered; under `--json` that line is left out). `--json` prints one object per line with the keys `repo`, `subject`, `kind`, `action`, `fingerprint` and `handoff`; a ruling's object adds `forms` (the `**Ruling:**` forms of the choices still open) and `on` (the issue URL the ruling is posted on), and a `merge` or `proceed` object adds `head`, the head it covers. An empty store prints nothing.

One line per item:

    <repo> <unit or review> | <kind> | <action>

The action is `answer in the inbox` for a ruling this skill asks, `answer in your <skill> session` for a ruling a review's own interactive session asks in words, or the merge, machine or setup step the item names. The kinds:

- `decision`: an open point-3 or point-5 decision; its forms are `**Ruling:** (<comment id>) <option> — <reason>` when its source is a comment, else `**Ruling:** (<decision id>) <option> — <reason>`, one per option of the record's `options` (the menu `(<a> | <b>)` of 1.2), `<option>` when it has none; an option whose text holds ` — ` is named by its letter, `(a)`, since the form's first ` — ` starts the reason.
- `cap`: a review at its cap with no `stop` ruled. A head's pending point-2 decision is answered in the inbox with the forms `**Ruling:** one more round | **Ruling:** stop | **Ruling:** redesign — <reason>` (one form per choice, the reason with `redesign` alone); the next `/superegm:wave <spec>` records the posted ruling. A head at its cap with no such decision open yet has no forms and the action `its decision point 2 opens at the next wave`: a ruling posted now would name no open decision and be dropped, so ask nothing and kick (step 10); the wave opens the decision and the item comes back with its forms. A spec, plan or integrate review's cap is `answer in your review-spec session`, `answer in your review-plan session` or `answer in your integrate session`, the session recording it with `superegm review rule --review <id> --ruling continue|accept|stop --owner`; on a chained handoff (the chain on and a frozen mode) a plan review's cap is not listed here, since the driven review-plan's wait record (the `waiting …` line) asks it. A spent choice leaves the forms: `one more round` once ruled on the unit, `continue` once ruled on the review.
- `contested`: a point-1 decision's contested finding, the forms `**Ruling:** <fid> finding upheld | **Ruling:** <fid> finding overruled — <reason>` (the reason with `finding overruled` alone).
- `merge`: the latest round's `outcome: clean`, or a `proceed` on the head, with its `head` the head that verdict covers; offered only while the unit is not stopped, no decision is pending, its latest launch has ended, its pull request does not read CONFLICTING and no `proceed` waits on a new pinned head. The action is the PR's URL, or the proceed's pinned head as 1.2 printed it, `await-merge after <units>` first while the merge order holds it; either way the inbox runs the merge (step 9), never the owner.
- `conflict`: a unit whose pull request reads CONFLICTING, information naming what resolves it (a merge round the next `launch` marks, the next fix round, or the owner's hand for a stopped unit or a 1.2.0 approval); no merge is offered while it lasts, and the inbox asks nothing.
- `stalled`: a head review that stalled (`review status` exit 5); a stall opens no decision, so it is answered in the inbox with the form `**Ruling:** proceed — <reason>`, the way past a stall.
- `proceed` (the owner's proceed again): a `proceed` a later launch outran, a pull request whose head is no longer the proceed's pinned head, or a proceed without a pinned head once the pull request has one; its `head` is the head a new proceed would cover, answered in the inbox with the form `**Ruling:** proceed — <reason>`.
- `escalated`: a pair of the approval record's `escalated[]` that neither the spec's `## Units` section nor a unit's decision names yet, or a plan's `blocking: yes` D<n> line not yet answered: `answer in your plan session` (`/superegm:plan <spec>`, which asks it; on a chained handoff the plan's D<n> line is the wait record's instead, and not listed here); or an integrate round's escalated finding, `answer in your integrate session`: the inbox asks nothing, and the owner's answer is recorded with `superegm review settle --review <id> --finding <fid> --disposition fixed | declined --owner` in that session, in leavemealone-mode a high or medium one's `--owner --posted <comment id>`, the id of the `**Ruling:** <fid> finding overruled — <reason>` comment that rules it.
- `redesign`: a unit a redesign ruling ended; `/superegm:brainstorming <brief>`, a typed step.
- `test-delta` and `owner`: the owner's own findings, the form `**Ruling:** <fid> allowed — <reason>` (in leavemealone-mode, for a finding an open point-1 decision asks about, `**Ruling:** <fid> finding overruled — <reason>`, the form `decision rule` takes there), until the finding is settled or ruled.
- `kill_failed`: a launch whose process could not be ended; not yet listed, until the launch records `kill_failed`; its `/superegm:interrupt` stays a typed machine step.
- `wave`: an open `wave` card with its age, information and never an action. The driver's `/superegm:driver reset`, `register` and `install` lines stay typed setup steps.

Never listed: builders running, rounds in progress, heads waiting on CI, lows, or the judges' converged rulings.

## Answering

The inbox runs in the owner's interactive session and writes only on an answer the owner gave in it.

1. **Who may answer.** Before acting on any answer, read `gh api user --jq .login` and refuse, acting on nothing, unless the login is in `config.owners` of the item's store. Every comment is posted with that login, so every ruling reader sees the owner's comment as if typed.
2. **The pick.** Open every question with one recommended option and a one-line reason ("I'd rule (b): the builder's test covers it. Rule (b)?"), picked from the question and its evidence: the round's `comments.md` and diff, the builder's comment, and `judges/<panel>/verdict.json`'s split where a panel ran. The owner's "yes" takes it; the owner may answer anything else in words instead.
3. **In leavemealone.** The judges settle each ruling and `decision rule … --by judges:<panel>` posts it, so ask nothing about those. Ask only what stays the owner's: a question the panel did not converge on, a `redesign`, an `owner:` or test-delta finding, a `kill_failed` unit, a merge and a wait before filing the frozen mode leaves to the owner, each with its pick.
4. **A ruling** (`answer in the inbox`: a decision, a contested finding, a head's cap, a test-delta or owner finding). Show the question, its forms as options and the pick; map the owner's words to one form and read the mapped ruling back once ("rule (b) — <reason>?"). On yes write it to a file and post it with `gh issue comment <n> -R <repo> --body-file <file>`, `<n>` and `<repo>` the item's `on`; the next wave session records it with `--posted`. Answers that map to no form are asked again, never posted.
5. **`proceed again`** (a `proceed` or `stalled` item). Show the item's `head`, the head the proceed covers (for a stall, the unit's head), then ask the owner for a one-line reason, read `**Ruling:** proceed — <reason>` back once and, on yes, post it on the item's `on` as above.
6. **A wait before filing** (a `waiting <phase>: …` line). Show the record's question; on the owner's answer run `superegm next answer --handoff <id> --answer <text>`, which reads the login itself and writes the answer into the wait record; the driven skill records it. For file's Create, show `handoff_dryrun.md` with the question first.
7. **Nothing left to plan** (`waiting plan: no unit left to plan`). Ask "void the approval?" and on yes run `superegm approve-spec --void --spec <spec>`, which opens and closes its own `approve-spec` card.
8. **A review's session** (`answer in your <skill> session`). Tell the owner which session asks it; ask nothing here.
9. **Merging.** For a merge item ask "merge <PR>?" naming its head `<sha>`, the item's `head` (the head its clean or proceeded verdict covers), never the pull request's live head. Merge only the pull requests the owner named in that answer: never one the owner did not name. Offer and merge in the shared-file merge order: a unit whose item `merges after` an unmerged unit (`await-merge after <units>`) is offered after it. `<repo>` is the item's store's repository, carried as `-R <repo>` on every `gh pr merge` and `gh repo view` here, `--admin` included. `<method>` is the first of `merge`, `squash` and `rebase` the repository allows, read with `gh repo view -R <repo> --json mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed` (`gh pr merge` without a method fails outside a terminal). Right before each merge, the ordinary one and the `--admin` one alike, read the unit's state again: the unit not stopped, no respec mark, no pending decision, no live launch, and the head's review verdict clean or proceeded. `superegm inbox --json --handoff <id>` lists the merge item again, with the same `head`, only while the unit is not stopped, no decision is pending, no launch is live and the verdict is clean or proceeded (and the pull request is not CONFLICTING, no proceed waiting on a new pinned head); a respec mark withdraws the offer too, though no store records one before U86, so the listing reads none; and read the pull request's head with `gh pr view <n> -R <repo> --json headRefOid`, which must still be `<sha>`. When any of these changed since the question, merge nothing: withdraw the offer with `superegm inbox withdrawn --pr <n> --reason <text> --handoff <id>`, the item's handoff filled in, which journals `merge withdrawn <PR> <reason>`, and tell the owner why. Otherwise run `gh pr merge <n> -R <repo> --<method> --match-head-commit <sha>`. A head that moved since the question is withdrawn like any other change, never merged; its merge is asked again, with the new head, once a clean or proceeded verdict covers that head and the listing offers its item. When GitHub refuses because the base branch's rules block the merge, ask "merge with the admin bypass?" and add `--admin` only on yes, after reading the state again as above.
10. **The kick.** After each posted ruling, written answer, void or merge, and for a head cap with no decision open yet, run `superegm driver kick --root <root>`, `<root>` the item's store's registered root: the `root` of the `registry.json` entry whose `artifacts_dir` is the item's store's, as the driver finds it, for the current store too (it may be a base worktree other than the current repository); with no such entry the store has no driver, so kick nothing.

The inbox opens no run card and runs no recorder, except three helper calls: `approve-spec --void`, which opens and closes its own `approve-spec` card; `driver kick`, which starts the tick; and `superegm inbox withdrawn`, which, typed without `--runcard`, opens and closes its own inbox card around its journal line. The phase session that holds the card records what the inbox posted or wrote.

## Notify

`wave` notifies, never this skill: after each batch's `report` it runs `superegm notify --runcard <card>`, which writes the card's handoff's lines new since `state.json.notified` to the owner's `~/.superegm/notify` hook (absent means no hook), bounded by `config.notify_timeout_seconds`.
